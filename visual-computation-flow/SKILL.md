# 保序计算流:从源码到一张图

一份完整的材料是**三层**,顺序不能倒:

0. **源码摘录** —— 编排骨架、同步标志、顶层参数表,让读者先看到"代码长什么样"
1. **计算流** —— 源码里所有产生数值的语句,按执行顺序排成一条线,每行注释「公式 + 精度 + `文件:行号`」
2. **计算流图** —— 把这条线按段折成节点,按执行单元上色

图是从流里长出来的。**先有流再有图**;直接照着理解画图,画出来的是你脑子里的印象,不是代码。

**第 1、2 层都不替代第 0 层。** 源码摘录是**基础需要**,计算流是**建在它之上的进一步分析**,不是它的压缩版。**不要因为写了计算流就把源码块删掉** —— 那是把基础层换成了衍生层,读者失去了核对的地基。

## 为什么是这个形式

读 kernel 最贵的不是看懂某一行,是**在几百行 buffer 管理、同步、多核分配里把"到底算了什么"捞出来**。捞出来之后,三个通常要单独查的问题会一起被回答:

- **公式落在哪几行** —— 注释里的公式就是索引
- **精度在哪掉的** —— 精度标在同一行,不用再翻一遍类型声明
- **谁依赖谁 / 哪段是串行的** —— 顺序本身就是答案

所以这三样必须写在**同一条注释**上。分开写成三份材料,读者要自己对齐,就白做了。

## 零、先摘源码(不要跳过)

在提流之前,先在材料里放一节源码摘录。摘什么:

- **编排骨架** —— kernel 入口 / `Process()` / 每条并发流的主循环,保留同步语句和循环结构(这些在计算流里会被删掉,所以只有这里能看到)
- **顶层参数表** —— 各 stage / 各函数的实参列表。**这是跨阶段数据流的权威证据**:哪个量传给了谁、哪个量根本没传,看参数表比看函数体可靠,后面画图判断依赖就靠它
- **一到两条带原始注释的关键片段** —— 尤其是源码自己解释了"为什么"的地方(比如 `// 读完之前AIV不能写` 这种直接点出反依赖的注释),原文照抄比你转述有力

摘录用大段 `文件名:起-止行` 标注,允许用 `// ...` 省略搬运和 buffer 管理。目标是让读者**能对着它核对后面的每一条流和每一条边**,不是让他读完整个 kernel。

## 一、先定口径

同一个算子往往有多个 arch / dtype / causal 分支,**行号只对一个版本成立**。开头一句话写清口径 —— 目标架构、dtype、走哪条分支、前向还是反向 —— 并给出这是默认路径的证据(哪一行的判定或断言)。不定口径,后面每个行号都可能对不上读者手里的文件。

## 二、抓"产生数值的语句"

判据只有一条:**这条语句执行完,有元素的数值变了吗?**

| 留 | 去 |
|---|---|
| 逐元素算术、超越函数、归约 | `DataCopy` / `memcpy` / load / store |
| 矩阵乘 / MMA / `IterateAll` / `tl.dot` | `Gather` / `Broadcast` / `Duplicate` / `reshape` / `transpose` |
| **`Cast` / 类型转换**(它改数值,是精度事件) | `SetFlag` / `WaitFlag` / `SyncAll` / `__syncthreads` |
| 标量取值后参与运算的 `GetValue` | buffer 申请、pingpong 切换、分核算下标 |

搬运和同步不是不重要 —— 它们是**另一份材料**(流水图、tiling 图)。混进来会把这条线淹掉:实测一份 900 行的 kernel,产生数值的语句只有 40 来条。

抓的时候用 grep 穷举,不要凭印象翻。按框架给起手式,**每条都分成「算数值的」和「改精度的」两组**:

| 框架 | 算数值的 | 改精度的(同样必须 grep) |
|---|---|---|
| **AscendC** | `Mul\|Muls\|Add\|Adds\|Sub\|Exp\|Ln\|CumSum\|MulAddDst\|ReduceSum\|Max\|IterateAll\|Iterate` | `Cast` |
| **Triton** | `tl\.(dot\|exp\|log\|sum\|max\|cumsum\|where\|sigmoid\|fma)` + 所有 RHS 带算术运算符的赋值 | `\.to\(tl\.` |
| **CUDA / CUTLASS** | `mma\|wgmma\|gemm\(\|__expf\|__fmaf\|fma\(` + 手写 elementwise 循环体 | `cute::transform\|__float2\|__bfloat162\|convert_type\|NumericConverter\|BF16\(\|FP16\(` |
| **TileLang** | `T\.gemm\|T\.reduce\|T\.exp` + `T.Parallel` 循环体里的算术(`T.copy` 排除) | `\.astype\|T\.cast` |
| **PyTorch 参考** | 所有非 view 的算子 | `\.to\(\|\.float()\|\.half()\|\.bfloat16()` |

**两组必须分开跑,不能合成一条正则一次过。** 合着跑你会得到一份混在一起的行号表,然后按"算数值的"那套心智去标注,降档语句就静静混在里面被当成搬运略过了。分开跑,第二组的结果是一份**独立的清单**,你会被迫对每一条回答"它降的是哪一发的输出"。

grep 出来的行号**直接抄进注释**,不要事后回忆。这份材料的读者通常比你更熟这块代码,一个错行号就废掉整份的可信度。

## 三、按执行顺序排,不是按文件顺序

这是最容易错的一步。**顺序来自调用链**:从 kernel 入口(`__global__` 函数 / `Process()` / `main` 循环)往下走 —— 一个函数定义在文件第 460 行、却被调用在第 380 行,它就排在 380 那个位置,不是 460。

遇到**两条并发流**(Cube/Vector、producer/consumer warp、多 stage kernel),不要画成两栏 —— 那是流水图的事。用同步点当偏序,把两条流**压成一条全序**:同步点两侧的相对顺序是确定的,同步点之间的谁先谁后随便挑一个稳定顺序即可。压完之后**同步语句本身删掉**,它已经体现在顺序里了。

跨 kernel / 跨 stage 的量,在流里就是"某一步写 GM、后面某一步读回来"。读回来那一步通常是一个 `Cast` —— 它同时是**依赖边**和**精度事件**,写注释时两件事都要点出来。

## 四、每行三件事

格式固定:「源码语句 → **`[精度]`** 公式 → `文件:行号`」

```
<原样抄来的源码语句>
                          // [精度]  这一步算的公式                      :行号
<下一条语句>
                          // [精度]  公式                                :行号
//   ↑ 为什么要这么写:读者看代码看不出来的那半句
```

三列各有各的用处:**语句**保留源码变量名(读者能 grep)、**公式**用数学符号(能对回论文)、**行号**是可点击的出处。三样必须同行 —— 分开写成三份材料,读者要自己对齐,就白做了。完整的真实例子见 `references/worked-example.md`。

**公式用一套固定符号**,并在开头声明是哪一套(论文第几节 / 你自己推导的哪一小节)。源码变量名保留在语句里,公式用数学符号 —— 两套名字并排出现,才能双向索引。

**精度从源码里的类型参数读,不要从"应该是什么"推**。模板实参、累加器类型、`out_dtype=`、`cT` 之类的输出类型 —— 都要有出处行号。记号建议:

| 记号 | 含义 |
|---|---|
| `[f32]` | 向量/标量单元上的 FP32 逐元素 |
| `[bf16→f32]` / `[f32→bf16]` | 显式 Cast 升/降 |
| `[bf16·bf16→f32→bf16]` | MMA:输入 BF16、累加器 FP32、写出降 BF16 |

MMA 这一档必须写成三段,因为**"累加器是 FP32"和"结果落盘是 BF16"是两件独立的事**,只写一个都会误导。

**第三段是最容易漏的一处,而且漏了不只是记号不全 —— 它会让读者读错依赖。** 成因是结构性的:降档几乎从不写在 GEMM 那一行,而是**紧跟其后的一条独立语句**(`cute::transform` / `Cast` / `.to()`)。你按"产生数值的语句"去抓,抓到的是 GEMM;那条 transform 长得像搬运,顺手就跳过了。于是标出来是 `[bf16·bf16→f32]`,停在累加器上 —— 读者据此认为这个量以 FP32 传给了下游,而实际下一发 GEMM 拿到的是 BF16。**这是一个会传播的错**:它同时污染流、图上的节点精度、和边的语义。

固定的核对办法,做完 §四**必须跑一遍**:**从 GEMM 那一侧倒着查,不要从 grep 结果正着查。** 逐发问"这一发的结果去哪了",然后两个方向各查一遍:

- **每一发"需要接力"的 GEMM 都必须找到一条降档语句。**"需要接力"= 它的结果又成了后面某一发的 A/B 操作数。这类 GEMM **一定**有降档 —— 不是风格问题,是硬约束:MMA atom 的操作数格式写死在类型里(`..._F32BF16BF16F32_TN` 的 A/B 必须 BF16),FP32 累加器物理上喂不进去。**找不到就是漏抓了**,不可能是"这一发碰巧不用降"。
- **反过来,grep 出的降档语句里,多出来的那些降的是落盘/输出**(结果不再喂 GEMM,只是写回)。数量对不上不一定是错,但**每一条都要说得出属于哪一类** —— 说不出,就是你还没搞清这个量的去向。

**为什么必须从 GEMM 倒着查:降档不一定是一条独立语句。** 它可能内联在别的表达式里(`S = BF16(f32(S)*g + acc)`),被正则漏掉。以 grep 结果为准,你会漏一次;以"每发 GEMM 的结果去哪了"为准,漏不掉 —— 因为 GEMM 本身是好抓的。

这个分类顺带回答了下一个问题:**这次降档是硬约束还是主动选的?** 接力那类没有讨论余地;落盘那类才是设计取舍,值得写一条"↑"说明为什么选这个格式。两者混为一谈,会把"没得选"说成"选错了"。

**加"↑"续行注释解释"为什么"**:为什么这个量要重算而不是读回、为什么某个系数被提前折进上游张量、为什么这里多做了一次看似冗余的掩码。这些是读者自己看代码看不出来的部分,也是这份材料唯一不可替代的价值。

## 五、分段:一段 = 图上一个节点

把流切成 5–12 个编号段。切法:**一段 = 共享同一个公式、同一个执行单元的最长连续行**。

段太细(每行一个节点)图上全是框,看不出结构;段太粗(一个 stage 一个节点)图退化成原来那张流程图,白画。判据:每段要能用一句话说清"这段算出了什么",说不清就是切错了。

段号 ①②③… 同时用在流和图上,**两边的编号必须一致** —— 这是读者在图和代码之间跳转的唯一凭据。

## 六、画图

mermaid `flowchart TB`。一个节点 = 一段,标题栏放段号+名字+精度,正文放公式,末行放 `─ file.h:LINE`。

**按执行单元上色**,这是整张图信息量最大的一处:

```
classDef vec  fill:#e8f1fb,stroke:#3f6fa8,stroke-width:1.5px,color:#12263f
classDef cube fill:#fdf1e3,stroke:#c8853a,stroke-width:1.5px,color:#4a2f12
class A1,A2,A5,B1,C1 vec
class A4,A7,A9,B2,B3 cube
```

颜色一换就是一次跨单元交货。在异构单元上,**跨单元交货点几乎总是精度降档点**(经共享内存/GM 交货,交货格式定死了精度)。于是「颜色交替次数 = 交互次数 = 降精度次数」,这条等式是图相对文字的净增量。

`subgraph` 分 stage,串行的那个 stage 单独换个底色 + 加粗边框。

### 边:必须分类型,而且标源码原名

图上最容易蒙混过关的就是连线。**箭头看上去都一样,但语义可能完全不同**,读者会把它们全读成"依赖",于是从图里得到错误的结论。规矩两条:

**1. 实线 = 真实数据依赖,虚线 = 不传数据的边。** 后者包括:跨 chunk / 跨迭代的回边、纯 `SyncAll` / barrier 造成的执行序、WAR 反依赖(下游要写、必须等上游读完 —— 数据是反向的)。画之前对每条边问一句:**"箭头尾巴那个节点算出来的数值,有没有流进箭头头上那个节点?"** 答否就是虚线。图上必须配一句 legend 说明实线虚线各是什么,并**点名有哪几条虚线**。

**2. 每条实线的 label 写源码里那个变量的原名**,不要写数学符号 —— 写那个 GM/SMEM buffer 在代码里叫什么,读者想核对就直接 grep 这个名字。数学符号留在节点正文的公式里;边上放原名,节点里放公式,两者并排才能双向索引。

对边的两个高频错误,都要专门查一遍:

- **把并列的兄弟画成了链。** 若干步各自读**同一个**上游量(fan-out / 菱形),很容易被顺手画成 `B1→B2→B3` 的串。判据:回源码看它们各自的**入参**是不是同一个变量;是,就是从那个变量拉出多条边,不是首尾相接。串起来会凭空捏造出并行度不存在的假象。
- **变量名对不上的依赖。** 字段名和实际写进去的值不一致是常事:形参名与实参名不同、名字暗示的是 `exp(x)` 而里面存的是 `x` 本身、变量名描述的是它上一个用途。**以顶层调用处的实参为准,不要信字段名**;发现这种就在边上或注释里明写这个坑,这类陷阱正是材料的价值所在。

### 踩过的坑

- **`<` 会被当 HTML 标签吃掉**。`Σ_{j<i}` 渲染出来整行塌掉。写成 `j 只取 0..i−1`,或用 `&lt;`。
- **不要画 subgraph → subgraph 的边**(`S1 ==> S2`)。mermaid 会把 S2 放到 S1 左边、边上的 label 甩出画布。**跨 stage 的边一律画在节点之间**(`A9 --> B2`),布局才是从上到下的。
- **一个 subgraph 如果没有任何入边,dagre 会把它排到最前面**,结果最后一个 stage 横着甩到第一个 stage 左边,整张图变成又宽又扁。若某个 stage 确实不接收上游数据(纯执行序),就补一条**虚线控制边**指向它的入口节点 —— 既修布局,又正好把这条边的语义如实标出来。
- **渲染窗口高度不够会从底部裁掉**,而且裁得很安静。渲染完**必须把 PNG 读回来目检**:最后一个节点在不在、边 label 有没有被切。图长了就把 headless 窗口调高重渲。
- 节点内用 `<br/>` 换行;用全角空格做右对齐比 padding 稳。

## 七、验收

六条,缺一条这份材料就不敢用:

1. **每个行号都是 grep 出来的**,不是回忆的。抽查三个,打开文件对一遍。
2. **源码摘录还在**,而且计算流里的每一段都能在摘录里找到对应的代码位置。
3. **公式覆盖表**:列一张「公式 ↔ 哪几段」的表,把参考公式逐条对进去。有公式对不上任何一段,说明漏抓了语句;有段对不上任何公式,说明这段的定位没想清楚。**这张表是完整性的唯一证据。**
4. **精度闭合**:沿着流从头走到尾,每个量**离开上一段时的格式**和**进入下一段时的格式**必须对得上。对不上就是中间有一条降档语句没抓到 —— 回 §二 用"改精度的"那组正则再 grep 一遍。第 3 条查的是"算全了没有",这一条查的是"精度标全了没有",**两者查的是不同的漏**:公式全对得上、精度照样可以整条错。
5. **每条边过一遍**:实线的 label 是不是源码里能 grep 到的变量名?这个数值真的从尾流到头了吗?虚线是不是都在 legend 里点了名?——一条画错的边比十个错行号更能误导读者。
6. **图读回来目检**,并写三句"这张图一眼能看出什么"。写不出来就说明分段错了,回第五步重切 —— 一张说不出新信息的图是装饰,不是材料。

最后补一节**未覆盖**:哪些分支读了没展开、哪些没读。边界不清的材料,读者只能整份不信。

## 完整例子

`references/worked-example.md` —— 走完七步的一份真实材料,素材是公开仓 [MoonshotAI/FlashKDA](https://github.com/MoonshotAI/FlashKDA)(CUTLASS/CuTe,SM90),每个行号都能自己 clone 下来核对。**卡在哪一步就翻到那一节看**:定口径怎么给证据、grep 起手式的实际产出长什么样、"↑ 为什么"注释该写什么、三种边怎么分、以及渲染时踩的三个坑(subgraph 排错位、`<` 被吃掉、必须读回目检)。

其中**四(d) 是一个失败案例**:那份材料第一版就漏了 §四 说的第三段精度,把 GEMM 标成 `[bf16·bf16→f32]` 停在累加器上,直到读者反问"这个量到下游怎么变 BF16 了"才发现。想知道这个错长什么样、怎么用发数核对查出来,直接看那一节。

## 与其他 skill 的关系

- 完整的算子研究流程(论文 → 计算流 → 精度 → 流水图)见 **operator-study**,这份 skill 是其中「② 源码 → 真实计算流」「③ 代码片段对应」「④ 标精度」三步的具体做法。
- 把这条流放进一份**完整材料**时,它在全篇的位置、与 demo/术语表/未覆盖各部件的关系、
  以及交付前的校验,见 **deep-tech-survey**。它把这条流当作"执行流图"这个部件来管。
  两处都会用到编号:**同一份材料里出现两套编号时的处理**(别让主干段号与局部编号同形)
  见它的 `references/document-skeleton.md` 的「编号是命名空间」。
- 这条流**不回答**"重叠得好不好、瓶颈在哪" —— 那要流水/时序图,是另一份材料。刻意不在这里混进同步和多 buffer,就是为了让这条线只回答"算了什么"。
