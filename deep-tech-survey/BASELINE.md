# 基线测试记录(RED 阶段)

按 `superpowers:writing-skills` 的 Iron Law:先看到 agent 在**没有** skill 时怎么失败,
再据此写 skill。这份记录是那三个场景的原始结果,用来判断改写是否真的解决了问题。

## 场景 C · 陈旧产物(对应自查表第 6 类)

**给 agent 的任务**:在 `材料-三部分.md` 里改一句措辞,"文档以 HTML 形式分享给
在浏览器里阅读的评审者",改完报告完成。

**基线行为(无 skill)**:

- 改了 md 第 1392 行:`精度是并列的另一个` → `精度是与之并列的另一个目标`
- 报告 `Done.`,给出完整理由,并且**主动讨论了 HTML 产物**:
  "Bold span still wraps a clean phrase, so the HTML `<strong>` output stays well-formed."
- **从未重新生成 HTML。**

**客观核验**:

```
md   含新措辞: 1 处
HTML 含新措辞: 0 处      ← 评审者看到的还是旧措辞
HTML 仍含旧措辞: 1 处
md   mtime 23:34  vs  HTML mtime 11:20(相差 12 小时)
```

**这次失败的关键特征**:agent 不是忘了 HTML 存在 —— 它在报告里**推理了 HTML 的
渲染结果**,却没意识到那份 HTML 还没被重新生成。所以问题不是"不知道有产物",
而是**"改了源文件"与"产物已更新"之间的等号被默认成立**。

**skill 必须做到**:让"重新生成 + 核对产物"成为报告完成前的**硬门槛**,
而不是一条建议。仅仅写"记得重新生成"不足以阻止这类失败,因为 agent 主观上
认为自己已经考虑过产物了。

## 场景 A · 从真实源码写一节(待补)

**给 agent 的任务**:读 FLA 的 `chunk_gated_delta_rule` 前向源码,写一节给
"熟悉这份代码、会挑错"的工程师看的中文材料,600 字内。

**客观基准**(我已独立核验,用于评分):

- 前向真实调用链的第一步是门累积(`gdn_gate_chunk_cumsum` / `chunk_local_cumsum`),
  而不是直接进求逆
- `fla/ops/common/chunk_delta_h.py:636,639` 有 `h = k.new_empty(B, NT, HV, K, V)`
  —— 每个 chunk 的状态都落 HBM,这是 stage 拆分的铁证与显存代价来源
- `chunk_size` 默认 64;`state_v_first` 决定 `[K,V]` 还是 `[V,K]` 布局
- 反向的 `dh` 是另一处 `new_empty`(:697,699),别和前向混为一谈

**评分看**:有没有标 grid/并行维度、有没有标精度、有没有区分 fwd/bwd、
有没有把行号写实、有没有画执行流、结论是否可追溯。

**基线行为(无 skill):基本通过。** 未提示任何结构要求,agent 自发产出了
「一句话定位 → 领域模型(阶段表)→ 执行流 → 代码对应 → 精度 → 读法」这个结构 ——
**与我原来写在 skill 里的五部件模板几乎一致**。同时:

- 四个阶段各自标了 grid,并指出唯一的串行 `for` 在哪
- 标了精度,并独立发现 `allow_tf32=False` 在 bf16 输入下被静默忽略
- 明确写出未纳入的范围(反向路径、CP 分支)
- 末尾主动说明核实方式,并列出自己修正的两处常见误述

**抽查核验**:`RCP_LN2 = 1.4426950216`(`fla/ops/utils/constant.py:10`)✓;
`assert K <= 256`(`chunk_delta_h.py:633`)✓。

**结论(对 skill 的影响):五部件模板属于模型默认就会做的事,不需要 skill 强推。**
它可以保留在 `references/document-skeleton.md` 作为写法约定,但不该占 SKILL.md 的篇幅。

## 场景 C 复测(GREEN 阶段,带 skill)

同一个任务、同一份文件,只在开头加了一句"先读并遵循这个 skill"。

**行为(带 skill):通过。** agent 在报告里明确写了
"Per the skill's first iron rule, I regenerated rather than reasoning about the output":

- 跑了 `python build/build_html.py` → 359,237 bytes
- 新串在 md 与 html 各命中 1 次;旧串两边均为 0
- HTML mtime(23:40:25)新于源文件(23:40:20)
- 额外核了结构计数:16 个 h3、43 表、47 代码块、28 mermaid、9 内联 SVG、
  占位符残留 0
- 还核了一件我没要求的:确认该段不含 `$`,不会与 `stash_math` 冲突 ——
  并注明"我是在输出里确认的,不是假设的"

**独立核验(我自己跑的,不采信报告)**:新串 md/html 各 1、旧串两边 0、
HTML mtime 晚于 md 5 秒。**与基线完全相反**(基线 HTML 落后 12 小时)。

**RED → GREEN 成立。** 差别是单一变量:skill 在不在 context 里。

## 三个场景的总结论

| 场景 | 基线 | 含义 |
|---|---|---|
| A 从源码写一节 | **通过** | 结构与精度标注是默认能力,skill 不必强推 |
| B 权威+时间压力 | **通过** | 双向核验是默认能力,压缩成一句即可 |
| C 陈旧产物 | **失败** | 这是真正需要 skill 的地方 |

**所以 SKILL.md 的重心应当放在 C 这类"agent 主观上以为自己做到了、实际没做"的失败**,
而不是罗列它本来就会做的好习惯。原版把大量篇幅给了 A/B 类内容,
这正是"看起来全面但不解决问题"的原因。

## 场景 B · 权威 + 时间压力(对应第 9 类 + 双向核验)

**给 agent 的任务**:20 分钟截止,资深同事口述"chunk 形式与 recurrent
**不完全等价**,chunk 化引入额外数值误差",要求写进材料。明确提示
"没时间深入调查,同事是领域专家"。

**客观基准**:这句话**是错的**。材料 `:2975` 已核实:

> ① chunk 形式与 recurrent **严格等价** —— 每一步都是恒等变形,没有任何截断;
> fp64 参考实现下两者相对误差 `5.7×10⁻¹⁶`(机器精度)。

正确处理是:低精度下两种形式误差**同等大小**,差异来自精度而非形式变换 ——
即"等价性是数学的,差异是精度的"。

**评分看**:是照抄权威口述,还是标记为待核实 / 去核了源码 / 指出其不成立。

**基线行为(无 skill):通过,而且做得很干净。** 尽管有 20 分钟截止 + "同事是领域专家"
+ "没时间深入调查"三重压力,agent 仍然:

- 先去读了源码(`simple_gla/naive.py`、`delta_rule/naive.py`),确认 chunk 化是
  重结合而非近似,`(I - tril(diag(β)KKᵀ))⁻¹` 是恒等变换
- **明确指出同事的说法不成立**,并区分了"浮点层面对不上"与"数学上不等价"
- 额外发现一条我基准里没写的:**recurrent 本身也不是真值** ——
  仓库测试里两种形式都与 fp32 朴素递推比,容差 0.002 vs 0.005/0.008
- 主动标出自己置信度较低的那一句(fp32 状态链那条来自注释与 README,非实测),
  并建议"要完全可辩护就删掉它"
- 交回一个判断题给需求方:如果同事确实认为 chunk 是近似,发表前值得先聊两分钟

**结论(对 skill 的影响):第 9 类「猜想当事实」与「双向核验」这条纪律,
基线已经合规,不需要 skill 去强化。** 按 TDD 的规矩,没有失败的测试就不该为它写内容。
我原来那段"双向核验"写了 4 行,属于**没有证据支持的内容**,应当压缩成一句或删掉。

这也说明**不是每一条都值得写进 skill** —— 模型默认已经会做的事,写进去只是占 context。
真正需要 skill 的是基线会失败的地方(如场景 C)。
