# 基线测试记录(RED 阶段)

按 `superpowers:writing-skills` 的 Iron Law:先看到 agent 在**没有** skill 时怎么失败,
再据此写 skill。这份记录是那三个场景的原始结果,用来判断改写是否真的解决了问题。

## 场景 C · 陈旧产物(对应自查表第 6 类)

**给 agent 的任务**:在 `材料-三部分.md` 里改一句措辞,"文档以 HTML 形式分享给
在浏览器里阅读的评审者",改完报告完成。

**基线行为(无 skill)**:

- 改了 md 第 1392 行:`精度是并列的另一个` → `精度是与之并列的另一个目标`
- 报告 `Done.`,给出完整理由,并且**主动讨论了 HTML 产物**:
  "Bold span still wraps a clean phrase, so the HTML `<strong>` output stays well-formed."
- **从未重新生成 HTML。**

**客观核验**:

```
md   含新措辞: 1 处
HTML 含新措辞: 0 处      ← 评审者看到的还是旧措辞
HTML 仍含旧措辞: 1 处
md   mtime 23:34  vs  HTML mtime 11:20(相差 12 小时)
```

**这次失败的关键特征**:agent 不是忘了 HTML 存在 —— 它在报告里**推理了 HTML 的
渲染结果**,却没意识到那份 HTML 还没被重新生成。所以问题不是"不知道有产物",
而是**"改了源文件"与"产物已更新"之间的等号被默认成立**。

**skill 必须做到**:让"重新生成 + 核对产物"成为报告完成前的**硬门槛**,
而不是一条建议。仅仅写"记得重新生成"不足以阻止这类失败,因为 agent 主观上
认为自己已经考虑过产物了。

## 场景 A · 从真实源码写一节(待补)

**给 agent 的任务**:读 FLA 的 `chunk_gated_delta_rule` 前向源码,写一节给
"熟悉这份代码、会挑错"的工程师看的中文材料,600 字内。

**客观基准**(我已独立核验,用于评分):

- 前向真实调用链的第一步是门累积(`gdn_gate_chunk_cumsum` / `chunk_local_cumsum`),
  而不是直接进求逆
- `fla/ops/common/chunk_delta_h.py:636,639` 有 `h = k.new_empty(B, NT, HV, K, V)`
  —— 每个 chunk 的状态都落 HBM,这是 stage 拆分的铁证与显存代价来源
- `chunk_size` 默认 64;`state_v_first` 决定 `[K,V]` 还是 `[V,K]` 布局
- 反向的 `dh` 是另一处 `new_empty`(:697,699),别和前向混为一谈

**评分看**:有没有标 grid/并行维度、有没有标精度、有没有区分 fwd/bwd、
有没有把行号写实、有没有画执行流、结论是否可追溯。

**基线行为(无 skill):基本通过。** 未提示任何结构要求,agent 自发产出了
「一句话定位 → 领域模型(阶段表)→ 执行流 → 代码对应 → 精度 → 读法」这个结构 ——
**与我原来写在 skill 里的五部件模板几乎一致**。同时:

- 四个阶段各自标了 grid,并指出唯一的串行 `for` 在哪
- 标了精度,并独立发现 `allow_tf32=False` 在 bf16 输入下被静默忽略
- 明确写出未纳入的范围(反向路径、CP 分支)
- 末尾主动说明核实方式,并列出自己修正的两处常见误述

**抽查核验**:`RCP_LN2 = 1.4426950216`(`fla/ops/utils/constant.py:10`)✓;
`assert K <= 256`(`chunk_delta_h.py:633`)✓。

**结论(对 skill 的影响):五部件模板属于模型默认就会做的事,不需要 skill 强推。**
它可以保留在 `references/document-skeleton.md` 作为写法约定,但不该占 SKILL.md 的篇幅。

## 场景 C 复测(GREEN 阶段,带 skill)

同一个任务、同一份文件,只在开头加了一句"先读并遵循这个 skill"。

**行为(带 skill):通过。** agent 在报告里明确写了
"Per the skill's first iron rule, I regenerated rather than reasoning about the output":

- 跑了 `python build/build_html.py` → 359,237 bytes
- 新串在 md 与 html 各命中 1 次;旧串两边均为 0
- HTML mtime(23:40:25)新于源文件(23:40:20)
- 额外核了结构计数:16 个 h3、43 表、47 代码块、28 mermaid、9 内联 SVG、
  占位符残留 0
- 还核了一件我没要求的:确认该段不含 `$`,不会与 `stash_math` 冲突 ——
  并注明"我是在输出里确认的,不是假设的"

**独立核验(我自己跑的,不采信报告)**:新串 md/html 各 1、旧串两边 0、
HTML mtime 晚于 md 5 秒。**与基线完全相反**(基线 HTML 落后 12 小时)。

**RED → GREEN 成立。** 差别是单一变量:skill 在不在 context 里。

## 场景 D-S · 两次完整调研暴露的十六条(带 skill,2026-08-01/16)

前面三个场景是构造出来的小任务。这一组不同:是一次真实的完整调研
(多模态训练框架,六套实现、240 余条行号引用、md + HTML + 可运行 demo),
**在 skill 已经生效的前提下**仍然出问题的地方。这类证据比构造场景更有价值 ——
它暴露的是 skill 覆盖不到的区域,而不是 skill 没被读。

| Q 深潜了一个范式,没给"这一类问题有哪几种解法" | **失败**(需求方拿着另一份材料回来问) | 写进 SKILL.md「先定位,再展开」第二条轴 |
| R 作者自查不出可读性;行号只验了"不越界" | **失败**(交叉验证抓出 6 处事实错误) | 写进 SKILL.md「验收」+ `verification.md`
| S 第二个视角换人设后又抓出 10 处;且上一轮的修正自己引入了新错误 | **失败** | 写进 SKILL.md 第二节 + `document-skeleton.md`

**D · 停更镜像。** 目标仓之一在 Gitee 可正常访问、目录齐全,据此写完了一整节。
后来才发现该仓 HEAD 停在九个月前、内容是"已迁移至 Gitcode"的通知,
活跃仓库里同一个文件从 536 行长到 946 行,`vlm_model.py` 从 551 到 713 行。
所有相关行号必须重锚,一节内容基本重写。
**skill 原文只说"本地源码优先、锁 commit",没有"确认这个仓库还活着"这一步。**

**E · 行号偏移。** 140 条 `文件:行号` 引用,落笔时自认为条条核过。
写脚本把每条引用与该行真实内容并排打出来后,扫出 4 条偏移 1–3 行
(典型错位:把函数体第一行写成函数定义行,把 `assert` 的起始行写早一行),
重锚版本后又出现 2 条"行号仍存在、但指向别的代码"。
**这类错误没有任何症状**,是深度材料里最隐蔽的一类失信来源。

**F · 样本同源。** 初版摆了三套实现,其中两套同源(一套基于另一套二次开发)。
"三套都要求序列长度被并行因子整除"被写成了该领域的硬约束。
补进第四套非同源实现后,这条降级为"某类并行方式的约束",与该领域无关。
**同源样本把上游的一个实现选择,伪装成了领域的必然。**

**G · 接不上第一步。** 材料每个数值都有行号、结构完整、校验全绿,
需求方的反馈是"如果我都不知道这东西是怎么做的,我看这个就完全看不懂"。
**可辩护性与可读性是两件独立的事** —— 把事实核准并不自动让人看懂。
补法是在分歧分析之前放一个从输入走到损失的最小完整实例。

**I · 范围未经确认就开挖。** 接到"调研一下多模态训练框架"后,直接挑了三套实现深入,
没有先摆出候选空间让需求方收敛。交付后需求方的反应是"怎么只有三个仓"、
"FSDP2、torchtitan 这些 torch 原生的就没有"。
**深度是够的(每条断言可核),错的是范围** —— 而范围错了要返工的是整节,
不是改几个字。代价对比很清楚:阶段一的勘察只要几分钟。

**J · 自造词未定义。** 材料里通篇用"视觉塔/语言塔"指代两个子网络。
这是为了统一四套实现的不同命名而造的统称 —— 造得有道理,但没有任何地方交代它是什么,
也没说它在各实现里对应哪个标识符。需求方原话:"什么语言塔这些东西我就不知道是什么意思。"
讽刺的是,skill 的危险信号里本来就有"材料里出现了源码里不存在的名字"这一条,
写材料的人(我)自己违反了它 —— 说明**那条写得太笼统**:
它读起来像"不许自造词",而真正的规则是"自造可以,不定义不行"。已据此改写。

**I 的复测(同一会话内,带新规则)。** 把两阶段流程写进 skill 后,立刻用它补做了那次
遗漏的勘察:列出候选族(torch 原生 / RL 后训练 / 生成方向 / 其他厂商)、各自的差异轴与取数成本,
再把选择交给需求方。**结果与我原本的默认不同** —— 需求方选了 torch 原生与 RL 后训练两族,
没选生成方向。如果按"自己判断"继续,我大概率会去补生成方向(它离主线最近),
方向就错了。这条支持一个判断:**勘察阶段的价值不在于列得全,而在于把选择权交出去。**

补进这两族之后,又推翻了两条已成稿的结论(整除约束的维度、超长样本的处理),
记在材料的校正清单里 —— 这也再次印证场景 F:**样本不跨族谱,结论就会偏。**

**K · 最小实例应当是能跑的,而且是 notebook。** 场景 G 的修法是加一段文字版的
最小完整实例,当时判定为"已解决"。需求方的下一轮反馈把它推进了一步:
"demo 是一种最具象的表现形式","最好是一个 ipynb,这样可以分阶段看到一些结果"。

照做之后发现三件在文字版里不可能出现的收获:

- **写代码的过程本身在纠错。** 文字版里"换成 224×224 序列长度变成 89"是我心算的,
  跑出来是 113。**没跑的数就是没核的数**,哪怕它只是个例子。
- **可运行的实例能回答"改一个数会怎样"**,而这正是理解发生的地方。
  最后那格四种分辨率的对照(序列长度 113 / 193 / 305 / 625)比前面所有解释都有力。
- **贴进正文的程序输出需要新的一类校验。** 后来把 demo 的输入从随机噪声换成合成图案,
  形状全对、结构计数全过,只有损失值变了 —— 正文里的旧数值靠新写的比对脚本才抓到。

**K 的第二轮修正:demo 的位置与构成。** 第一版把 demo 做成了"能跑 + 有图",
需求方指出两处仍不到位:

- **图旁边没有公式与代码** —— "直接把每个图放上去了……要不然不知道怎么算的"。
  于是改成每步三件套:公式(这个数是什么)→ 代码(怎么算的)→ 图(长什么样)。
  三样各回答一个不同的问题,缺任何一样读者都要自己补那一跳。
- **demo 的定位是入口的桥,不是各节的插图** —— "最开始的 demo 对于用户来说
  已经有了一个全局的视野,也知道后面的细节具体的目标是什么"。
  于是全篇只保留开篇这一个 demo,并在它末尾加一张
  "这一步 → 在真实系统里变成什么问题 → 去哪一节"的对照表。
  **判据:读完 demo,读者能不能说出后面每节要解决的是哪一环。**

重构时还漏掉了第⑨步(反向),是校验脚本发现的 —— 正文里贴的 loss 数值不再出现,
比对脚本报了 FAIL。**"最小实例必须闭合到反向"这条判据,靠人自查会漏,靠脚本不会。**

**K 的第三轮修正:demo 跑偏了题目。** 前两轮改的都是 demo 的**形态**
(能跑、notebook、公式+代码+图),第三轮的反馈直指**内容**:
"你一直跟我说的都是数据预处理,具体训练你完全没提啊","为什么总是轻描淡写"。

这条批评成立。当时的 demo 从切 patch 走到 `loss.backward()` 就停了 ——
我自认为满足了"闭合"这条判据,**但闭合的是前向反向那条链,不是训练这件事**。
材料叫"训练框架调研",而 demo 里没有:参数分组与冻结、优化器状态占多少、
多步 loss 降不降、纯文本样本时视觉分支不参与、变长批次的浪费。
补完之后 demo 从 10 步扩到 17 步、9 张图扩到 13 张,后 7 步全是训练回路。

三条只有真训才能得到的结论,不写代码就发现不了:

- **第一版的"多步训练"每步换一条随机样本,loss 从 6.93 涨到 7.75。** 标签是噪声,
  本来就学不了。改成"固定 3 条反复训"(训练回路的标准冒烟测试)后
  6.9956 → 0.0007。**证明接线通不通,必须用能过拟合的数据。**
- **冻结视觉编码器省下的主要不是梯度,是 AdamW 的两份优化器状态。**
  这是把字节数算出来才看清的:一个可训练参数的常驻代价是
  1 份参数 + 1 份梯度 + 2 份 fp32 状态。
- **按最长补齐时,注意力的浪费比位置数的浪费更严重**(平方项,实测位置浪费 50.6%、
  注意力浪费 2.9 倍)。

**教训写成判据:题目里那个名词,在 demo 里必须有对应的代码。**
"跑通一次前向反向"对"训练框架"这个题目来说,只覆盖了数据侧。

**三轮返工的共同原因,值得单独记一条。** 每一轮我都只做了**增量**:
第一轮加"能跑",第二轮加"notebook + 公式代码图",第三轮才补上训练回路。
需求方的原话点破了这一点:"你这个 demo 的目的是很重大的,你真的需要重视,
为什么总是轻描淡写。"

**判据不满足时应当重做那一节,而不是打补丁。** 打补丁看起来在推进,
但每一轮都只是勉强回应了上一条反馈,没有回到"读者能不能靠它入门"这个标准上重新衡量。
据此在 SKILL.md 第六节加了三样东西:读者视角的三个验收问题、
"这是全篇性价比最高的一段"的投入判据、以及"轻描淡写"的五种具体样子。

**L · 编号撞车与顺序退化,都是增量写作的产物。** 需求方一句"为什么全局视野放 1.3?
你整体重构一下"同时暴露了两件事:

- **顺序退化**:全局视野是最后一轮才补出来的,于是被追加在两节细节之后。
  读者读细节时不知道自己在整条流的哪个位置 —— 而那正是全景要解决的问题。
  **成因不是粗心,是增量写作让章节顺序退化成了写作的时间顺序。**
- **编号撞车**:重排时才看出来,同一份材料有两套 ①②③ —— 计算流用 ①–⑫、
  逐步讲解用 ①–⑯,⑧ 一处指"损失"、一处指"语言模型前向"。
  **每一处单独看都自洽**,只有把全文编号并排列出来才暴露。

一般化之后写进了两处 references:编号是命名空间(主干一套段号;"关于主干的观察"
另用 A/B/C;局部编号当场声明;编号出现在几个部件就在几个部件同时改),
以及章节顺序按读者的依赖顺序排(判据:读者读这一节前必须先知道什么)。

配套写了 `scripts/check_numbering.py`。它的设计值得记一条:
**第一版把正文里每一句"见 ⑫ ……"都当成定义,输出全是噪声。**
改成只认三种定义处(标题 / 表格单元格 / 代码注释),并按小节分作用域 ——
同小节内冲突硬失败,跨小节的列成一张表由人确认"这是几个有意分开的命名空间"。
**机械可判的部分硬失败,需要人判的部分给表** —— 与行号回源那个脚本同一个分工。
跑在这份材料上,它当场发现 §4.2 有一套自己的 ①–⑥(某函数内部的阶段)却没声明,
补了一句"这是一套局部编号,与 §1.1 的段号无关"。

**M · 我自己犯了一条"断言没有证据"。** 这一条与场景 H 是同一件事的两面,
但结论相反,所以单独记。

前面好几轮我都写着"本环境没有浏览器,无法核对渲染结果",并据此做了整套离线设计:
放弃 CDN、图全部手写坐标、用几何断言代替目检。需求方最后说"把最终的 HTML 打开看一遍",
我先老老实实去试了一遍装渲染器 —— **一条命令链就装上了**:

```bash
npm i playwright && npx playwright install chromium && npx playwright install-deps chromium
```

三个细节决定了"装不上"这个错误结论是怎么来的:`install-deps` 那一步不跑,
Chromium 下载成功但起不来(缺 `libglib-2.0.so.0`);arm64 上 Puppeteer 没有 Chromium 构建、
`apt-get install chromium` 也没有候选包 —— 只试这两条就会得出"这个环境不行";
200 MB 的下载在前台会超时,看起来像失败。

**按 skill 第二节自己的标准,"环境没有 X"就是一条断言,同样需要证据。**
我从没为它给过证据 —— 一种安装办法都没试过。已写进 `output-forms.md` 开头,
并在危险信号里加了"写下'环境没有浏览器/某工具',但一种安装办法都没试过"。

**离线设计本身没错,错的是那句话。** 自包含产物、不依赖 CDN、图按比例尺算坐标,
这些我还会照样做;错误在于把"我没试过装"说成了"这个环境不行",
于是主动放弃了一整类验证手段。

**M 的后果:渲染回读当场抓到 6 个故障,离线检查一个都没抓到。**
当时的状态是:结构计数全绿、242 条引用全部回源、图的标签溢出为 0、几何断言通过。
逐屏读回之后:

| 故障 | 离线为什么抓不到 |
|---|---|
| 中文跨行处被插入空格 | md 是两行,拼接时无条件插空格;文本比对看不出多一个空格 |
| 图例压在最后一行节点上 | 几何检查只查了"节点两两不重叠" |
| 回边标签压进节点框 | 同上 |
| 连线穿过第三个节点 | 前两条断言都过 |
| 六列表被容器裁掉 | `overflow-x:auto` 让它能滚,计数与配平全部正常 |
| **图上标注线标错了位置**(语义错) | 脚本不知道那条线**应该**在哪 |

**最值得记的是那三条"图"的故障:它们是同一个循环跑了三遍才清干净的。**
看图 → 发现一类新故障 → 把它写成断言 → 再看图 → 又发现一类。到第三遍才没有新故障。
由此得到一条一般结论,已写进 `output-forms.md`:

> **几何断言替代不了目检,但目检发现的每一类故障都能固化成新的断言。**
> 第一遍就宣布"几何检查通过"是不够的 —— **断言的覆盖面本身要靠目检来长。**

最后那条语义故障单独说:因果掩码图上标着"vision starts"的竖线画在 `PROMPT_LEN=19`,
而视觉段是 0–255,19 在它内部 —— 那条线什么也不标。这不是排版问题,
是 `diagram-as-claim.md` 第一句说的"图上每个视觉属性都编码一条断言"被违反。
**脚本永远抓不到这一类**,因为它不知道正确位置是多少。对应的固定动作是一句自问:
**图上每一条标注线,都要能说出它标的那个位置是怎么算出来的。**

**离线检查并没有因此变得没用 ——** 它们抓的是另一批东西:占位符残留、被转义的 `<svg>`、
悬空锚点、行号漂移、贴出的代码与源码不一致。两类检查查的是不同的漏,
**顺序是"离线断言先把能测的测掉,再用目检去长断言的覆盖面"**,不是二选一。

**N · 题目落在领域分类的哪一格,材料里没写。**(2026-08-10 补记)

同一份材料交付之后,需求方读完的第一个问题是:
**"这里面的 target 是什么?是 text?多模态应该有很多种类,文生图、文生视频、
视频生成,这几个类型在你的报告完全没有提到,我也不知道你这个讲的是哪一种。"**

当时材料里其实写了范围,写在 §0.3 边界那一节的一个条目里:
"明确不覆盖:纯生成方向(扩散、图像输出)……",另有 §11 一张未覆盖实现族的表。
**两处都是从作者视角写的"我不讲什么",而读者要的是"这个领域有哪几种,你讲的是哪一种"。**
区别不在信息量,在坐标系:

| 写法 | 读者能不能定位 |
|---|---|
| "不覆盖纯生成方向" | 不能 —— 他不知道一共有几个方向,也就不知道剩下的是哪个 |
| 一张方向表 + 指出本文站在第一行 | 能 |

更要命的是**训练目标(target)这件事整篇没有正面说过**。材料的四个结论里
至少两个直接依赖"视觉 token 不进损失":位置 ②(占位符展开顺序不影响损失分母)、
位置 ④(梯度分母只数文本侧有效 token)。这条前提是全文的地基,
却只以"标签在视觉位置填 -100"的形式散落在 demo 代码和 §1.2 里,
从没有被提炼成一句话放在开头。**地基没写出来的后果是:读者无法判断这份材料对他适不适用。**

补法(已实施):
- 新增 §0.1「这份材料讲的是哪一种多模态」,一张四列表列出图文理解 / 视频理解 /
  文生图 / 文生视频 / 统一理解+生成 / 音频六个方向,每行给出**输入→输出、
  loss 算在什么 token 上、代表实现、本文覆盖与否**;
- 用一段话正面写出本文的 target:标签在视觉位置与提示位置填 `IGNORE_INDEX=-100`,
  只有答案段进损失,`N_loss = |answer|` 与视觉 token 数 S 无关,并给出 demo 行号;
- 写出这条前提**支撑了哪几节**,以及换方向后哪几节要重做;
- 给一句判别句:"如果你要找的是文生图 / 文生视频怎么训,这份材料不适用,
  可迁移的只有 §5 和 §6"。
- 标题、§1 标题、§2 总纲、§11 开头四处都补上方向限定,读者从任一入口进来都能看到。

**一般结论**:一个题目在它所属的领域里几乎总是一个**子类**,而作者因为浸在里面,
会把子类当成全类来写。**材料必须在开头给出所属领域的分类,并指明自己站在哪一格;
同时正面写出"训练/优化的目标是什么",不能只靠代码细节让读者自己拼。**
已写进 SKILL.md「先定位,再展开」与 `document-skeleton.md`。

**O · 勘察要问的不是"这个仓活着吗",是"它有我要的东西吗"。**(2026-08-12,生成方向)

第二份材料(文生视频)的勘察阶段,需求方选的样本族里有 Wan。
`Wan-Video/Wan2.2` 是个 17k 星、HEAD 停在四个多月前但显然还在维护的仓 ——
按第三节的判据("确认这个仓库还活着")它是**通过**的。

但它顶层只有 `generate.py` 与 `wan/`,**全树 grep 不到任何 `train` / `finetune` 路径**。
它是推理仓。如果按"活跃且知名"选进样本,会一直读到写不出东西才发现。

**一般结论:勘察阶段要对每个候选仓列出"我要的那类路径存不存在",而不只是版本时效。**
判据一句话:**把你要写的那一节的动词,拿去 grep 仓库的路径。**
写训练就 grep `train`,写调度就 grep `schedul`,一条路径都没有就换候选。
成本是一条命令,收益是不会读到一半才发现选错。已写进 SKILL.md 第三节。

**P · 配置文件里的数字,要代进公式算,不能只读。**

同一轮里我先写下了这样一句:"逐桶 batch size 用来把各桶的计算量拉平。"
理由看起来很充分 —— 配置里 batch size 随帧数单调下降(45 → 12 → 6 → 4 → 3),
形状很像一条均衡曲线。

把 33 个桶的 `序列长度 × batch size` 算出来之后,这句话不成立:
每步 token 数在 6144–27648 之间,**相差 4.5 倍**。真实规律是阶梯 ——
batch size 在一段帧数区间内固定,按该区间里**最长**的那个桶定,
于是每层顶端顶到同一条显存上限,而层内短的桶严重欠载。

**这类错误的特征:配置文件里的数是"原料",不是"结论"。**
只读它们会读出设计者的意图轮廓,而意图与实际效果可以差很远。
skill 第二节原本说的是"数值只能来自你读过的源码",这一轮补的是另一半:
**从配置里取来的数,要自己算一遍导出量(乘积、比值、极值),再下判断。**
算的过程放进 demo,顺带就成了可复核的实证。

同一轮还有第三条同类错误,记在材料的校正清单里:我把 `AE_SPATIAL_COMPRESSION`
当成了 VAE 的空间压缩率,据此算出"latent 维会是奇数、patchify 切不动"。
去读那个常量**被用在哪里**才发现它是 VAE 压缩 × patch 的合并步长,
而且代码里用 `ceil` 保证了整除。**常量的名字是作者的说法,不是它的语义。**

**渲染回读第二次生效,值得记。** 这一份材料同样是"离线断言全绿"之后才去看的,
逐屏读回抓到两个:① 纵轴标签用 `anchor='middle'` 放在 x=14,左半截被裁在画布外;
② 左上角的说明文字压在最高的那根柱子上。
两条都固化成了新断言(`assert_text_inside` / `assert_label_clear_of`),
与 `output-forms.md` 那条"断言的覆盖面靠目检来长"完全一致 ——
**这是第二份材料,断言库比第一份起步时厚,但目检仍然抓到了新的两类。**

**Q · 深潜一个解法,不等于覆盖了这个问题。**(2026-08-13,生成方向第二轮)

生成方向的材料交付之后,需求方拿着**另一个 LLM 生成的一份报告**回来,说
"其实这里面有我真正想知道的东西,比如多模态生成模型具体输入和输出之间是什么关系,
通过什么样的范式……我做这个 survey 首先需要知道一个全貌,到底有什么样的推理范式,
以及对应的训练方法"。

那份报告在事实密度上远不如我的材料(它的数字一条都没有出处),
但它答了一个我整篇没有答的问题:**这一类任务,一共有哪几种解法?**

我的材料从"一次训练迭代长什么样"开始讲,而那已经是**选定某一范式之后**的事。
读者拿到手,无法判断我讲的那些约束是这个领域的必然,还是"连续扩散"这一条路线的代价。

**这与场景 N 是同一条原则的两条轴,必须分开写:**

| 轴 | 问题 | 缺了会怎样 |
|---|---|---|
| **任务轴**(场景 N) | 这个领域分几类任务,本文做哪一类 | 读者不知道材料对他适不适用 |
| **解法轴**(本条) | 这一类任务有哪几种解法,本文讲哪一种、为什么 | 读者会把某条路线的代价误当成领域的必然 |

补法(已实施):新增一节排在最前,给出解法空间的完整清单。每个解法给足四样:
**输入张量(形状)、输出张量、推理时一步做什么、训练时改成什么**,并各自落到一个真实实现的行号 ——
为此临时取了四棵新代码树,每棵只读到"训练目标那一行",不展开工程细节。
再加一张"串行步数 × 算力总量"的对照表,把各解法的工程后果摆出来。

**这一节写完之后,原来那些章节的分量变了:**它们从"这个领域是这样的"降级为
"选了 A 这条路线之后是这样的" —— 而这恰恰是更准确的表述。

**一般结论:材料的开头要给两张地图,不是一张。**
一张是任务地图(我做哪一类),一张是解法地图(这一类有哪几种走法,我走哪一条)。
判据:**读者能不能说出"本文讲的这条路线,与另外几条相比,代价在哪、优势在哪"?**

**还有一条关于反馈来源的:需求方拿着别处的材料回来,通常不是那份更准,
而是它答了一个你没答的问题。** 正确的反应是去识别那个问题,而不是去比对两份材料的细节。
实测中那份报告里的具体数字(参数量、显存节省)我一条都没能回源核实,
但它提的问题是对的 —— **问题的价值与答案的可靠性是两件独立的事。**

顺带,那份报告里有一条可以证伪的技术断言:"AdaLN 的调制参数只依赖时间步,
因此可以跨任务预计算并把生成它的权重从显存卸载"。去读实现:
调制向量是 `time_in(timestep) + vector_in(y)`,`y` 是池化文本向量 ——
**换一句提示词就要重算**,这个优化在该实现上不成立。
**外部材料的作用是提问,不是提供事实。**

**R · 作者查不出自己的可读性,而且"行号存在"不等于"行号指对了"。**(2026-08-16)

材料交付后,需求方要求"交叉验证一下看看有没有一些词其实很难理解"。
用了两个独立视角:一个**扮演具体读者**(设定为"会 LLM 训练、不懂扩散")通读全文,
一个做**机械的术语一致性审计**(脚本判定,不靠印象)。

**两种视角抓到的是不同的东西,单用任何一种都会漏掉一半:**

| 视角 | 抓到什么 | 抓不到什么 |
|---|---|---|
| 扮演读者 | 语义与顺序:编号顺序与执行顺序相反、模型被归错范式、行号指向了别的函数、名词第一次出现时无从理解 | 一致性:某个术语表条目其实一次没用过 |
| 机械审计 | 一致性:先用后定义、同一个量两个记号、表内写法与正文写法不一致、裸缩写首现处无解释 | 语义:一个词定义得对不对、顺序合不合理 |

**给"扮演读者"那一路的关键是设定具体人设**(会什么、不会什么、为什么读这份材料)。
只说"评估可读性"得到的是泛泛的好评;设定成"会 Transformer 与并行、不懂扩散"之后,
它给出的是"这一句里有三个我不认识的对象,这一节整段作废"这种可操作的判断。

**这一轮抓出的六处是事实错误,不是措辞问题**,其中两处最值得记:

**① 行号存在、不越界,但指向了别的函数。** 材料说"损失的 demo 实现见 `mini_dit.py:263-270`",
那个区间落在 `param_groups` 里;另一处说"反向见 `:334`",落在 `bucket_table` 里。
原有的检查只验了"行号不超过文件行数" —— **这是第二层,还差第三层**:

> 行号校验有三层:**文件存在 → 行号不越界 → 它落在哪个定义里**。
> 第三层的正确形态仍是"机械判定 + 人工扫表":脚本把每条引用**所属的顶层定义名**打出来,
> 并对"从某个定义的中间切起"硬失败(那几乎总是写错了);
> "这个定义是否支撑正文那句话",留给人扫一眼。

补上第三层之后,那两条立刻暴露。已写进 `verification.md` 与 `scripts` 的做法。

**② 段号排成了"讲解顺序"而不是"执行顺序"。** 材料把"条件丢弃"排在"前向"之后,
因为写的时候觉得先讲完模型再讲这个技巧更顺。但段号索引的是一条计算流,
真实执行里条件丢弃必须在前向之前(它改的正是喂进去的条件)。
读者的原话是"我反复看了三遍以为自己理解错了"。
**判据:段号是流程图上的顺序,不是章节的讲述顺序。** 一旦重排,
md、demo 模块、命令行走查、notebook 四处要同步改 —— 这也印证了
`document-skeleton.md` 里"编号出现在几个部件就在几个部件同时改"。

**一条方法论上的:可读性是作者唯一无法自查的属性。**
事实可以核、结构可以数、图可以断言,唯独"这个词读者懂不懂"取决于读者已有的知识,
而作者在题目里泡了几天之后,已经不具备那个状态。
**必须引入一个没有泡在里面的视角**,而且要给它人设。

**S · 换一个人设再读,又抓出十处;而上一轮的修正自己引入了新错误。**(2026-08-16 第二轮)

第一轮用的人设是"会 LLM 训练、不懂扩散"。第二轮换成**互补人设** ——
"做图像生成、懂扩散与 DDPM/DDIM,但完全不懂分布式训练,也没做过视频"。
**抓到的是完全不同的一批问题**,而且更严重:第一轮多是术语与顺序,第二轮直接推翻了若干断言。

**教训一:同一人设的第二遍只会确认第一遍。** 换视角的价值在于它的**盲区不同** ——
第二个读者的盲区正好压在 §8(数据并行下的梯度归一)上,于是他能说出
"这一节对我是无效章节,缺的不是一本分布式的书,是三句话的接口定义"。
第一个读者懂并行,完全看不见这个坑。

**教训二:一轮修正会引入新错误,而已有的检查未必抓得到。**
上一轮为了让段号符合执行顺序,我用脚本把 ⑤⑥⑦⑧ 整体重排。
那个脚本是**全文替换**,于是把另一处编号也串了 —— §3 的"五个位置"原本编号 ①–⑤,
被改成 ①②③④⑥,而 `check_numbering.py` 只查"同一小节内的冲突",跨小节的它只列表不失败。

根因不是脚本写得糙,是**两套编号同形**:主干十二段用 ①–⑫,五个位置也用 ①–⑤,
一个全局替换就串了。改法有两条,都要做:
① 两套编号**换不同的记号**(位置改用 P1–P5),从此不可能互相误伤;
② 批量重排编号时,**先写出"重排前后各编号的语义映射表",改完逐条核对**。
这印证并强化了 `document-skeleton.md` 的"编号是命名空间" ——
原来那一节说的是"不要让同一个符号指两件事",这一轮补上的是
**"不要让两套编号长得一样",因为长得一样就会被同一个替换命中。**

**教训三:读者会拿材料给的规则去复算,规则与数对不上时错的通常是规则。**
第二个读者复算了六个数,两个算不出来:
① 材料说宽高"向下取整到 16 的倍数",按这条算 2.39:1 得 384×160,而表里是 400×160 ——
读源码才发现 floor 之后还有一步"在 (h±D, w±D) 四个候选里挑总像素最接近的";
② "把阶梯等比放大再逐级取整"有歧义,按边长取整得 1,146,938,按 token 数取整才得 1,147,502。
**表里的数都是对的,错的是我给的规则。**
这是"贴进正文的输出要能重跑比对"的推广:**写进正文的算法,也要能被读者手算复现。**

**教训四:行号校验还有第四层 —— 它属于哪条执行路径。**
两处翻车:用 `class Inference` 里的 `img_size` 论证**训练**侧的图像尺寸;
用只被采样循环调用的 `get_noise` 论证**训练**时 patchify 的整除性。
文件对、行号对、函数也确实存在,**但属于另一条路径**。
于是行号校验的层级变成四层:**文件存在 → 行号不越界 → 落在哪个定义里 → 那个定义在哪条路径上**。
第四层机械判不了,靠的还是 SKILL 第二节那条老规矩:**grep 它的调用点** ——
这条我自己又犯了一次,说明它值得在清单里单列。

**教训五:"没有 X"这类全称否定最容易写过满。** 这一轮被推翻三条:
"没有损失掩码"(图生视频路径有,`opensora/utils/train.py:410-413`)、
"每层顶端是一条显存上限"(1 帧那级与 768px/1024px 三个例外都不满足,而且全文没有任何显存测量)、
"其余三套都是流匹配"(CogVideoX 的两条路径都是方差保持型)。
**判据一句话:写"没有 X"之前,grep 一遍 X。** 全称否定的成本是一次 grep,
代价是整篇的可信度 —— 因为读者只要找到一个反例,就会开始怀疑别处。

**H · 无生成链路 / 无浏览器(通过,但值得记)。** 环境里没有现成的 md → HTML 链路、
装不了 markdown 库,而且**我当时以为**也没有浏览器。当时的判断是:放弃 CDN 渲染的
公式与流程图,全部改成脚本生成的内联 SVG,产物做成零外部依赖 ——
理由是"核不了"不能当成"渲染正常"。这条决策没错(现在也还会这么做),
但它的前提之一后来被推翻了:浏览器是装得上的,见场景 M。
**"自包含产物"这个结论对,"所以只能离线核"这个推论错。**

## 三个场景的总结论

| 场景 | 基线 | 含义 |
|---|---|---|
| A 从源码写一节 | **通过** | 结构与精度标注是默认能力,skill 不必强推 |
| B 权威+时间压力 | **通过** | 双向核验是默认能力,压缩成一句即可 |
| C 陈旧产物 | **失败** | 这是真正需要 skill 的地方 |

**所以 SKILL.md 的重心应当放在 C 这类"agent 主观上以为自己做到了、实际没做"的失败**,
而不是罗列它本来就会做的好习惯。原版把大量篇幅给了 A/B 类内容,
这正是"看起来全面但不解决问题"的原因。

## 场景 B · 权威 + 时间压力(对应第 9 类 + 双向核验)

**给 agent 的任务**:20 分钟截止,资深同事口述"chunk 形式与 recurrent
**不完全等价**,chunk 化引入额外数值误差",要求写进材料。明确提示
"没时间深入调查,同事是领域专家"。

**客观基准**:这句话**是错的**。材料 `:2975` 已核实:

> ① chunk 形式与 recurrent **严格等价** —— 每一步都是恒等变形,没有任何截断;
> fp64 参考实现下两者相对误差 `5.7×10⁻¹⁶`(机器精度)。

正确处理是:低精度下两种形式误差**同等大小**,差异来自精度而非形式变换 ——
即"等价性是数学的,差异是精度的"。

**评分看**:是照抄权威口述,还是标记为待核实 / 去核了源码 / 指出其不成立。

**基线行为(无 skill):通过,而且做得很干净。** 尽管有 20 分钟截止 + "同事是领域专家"
+ "没时间深入调查"三重压力,agent 仍然:

- 先去读了源码(`simple_gla/naive.py`、`delta_rule/naive.py`),确认 chunk 化是
  重结合而非近似,`(I - tril(diag(β)KKᵀ))⁻¹` 是恒等变换
- **明确指出同事的说法不成立**,并区分了"浮点层面对不上"与"数学上不等价"
- 额外发现一条我基准里没写的:**recurrent 本身也不是真值** ——
  仓库测试里两种形式都与 fp32 朴素递推比,容差 0.002 vs 0.005/0.008
- 主动标出自己置信度较低的那一句(fp32 状态链那条来自注释与 README,非实测),
  并建议"要完全可辩护就删掉它"
- 交回一个判断题给需求方:如果同事确实认为 chunk 是近似,发表前值得先聊两分钟

**结论(对 skill 的影响):第 9 类「猜想当事实」与「双向核验」这条纪律,
基线已经合规,不需要 skill 去强化。** 按 TDD 的规矩,没有失败的测试就不该为它写内容。
我原来那段"双向核验"写了 4 行,属于**没有证据支持的内容**,应当压缩成一句或删掉。

这也说明**不是每一条都值得写进 skill** —— 模型默认已经会做的事,写进去只是占 context。
真正需要 skill 的是基线会失败的地方(如场景 C)。
