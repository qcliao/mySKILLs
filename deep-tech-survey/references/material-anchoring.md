# 材料怎么组织:锚点选错,读者就看不懂

## 按领域模型组织,不按代码命名组织

**最有价值的一条,来自一次明确的"看不懂"。**

读者的反馈往往只是"这一块不太清晰"。根因不是写少了 —— 表格里写的是 `mmResUb`、`tmpAFloorUb`
这类**变量名**,读者得自己反推每个变量在算法里是哪一项。

改法:**先立公式(领域模型),再让每个 buffer 去"认领"公式里的一项。**
两个阶段的分工于是自然浮出来,不需要额外解释。

推广:**代码的变量名是实现的偶然产物。** 跨版本、跨实现根本对不上 ——
按名字组织的表,读者看不出差异在哪。按领域概念组织(公式项、流程阶段、数据的生命周期),
两套实现才能左右对读。

**这条规则有代价,必须一起付:** 按领域概念组织意味着你要用一批**源码里不存在的词**
(各家标识符对不上,只能另起统称)。读者拿这个词去 grep 会一无所获,
于是"看起来像行话、其实查不到"。所以这条规则与术语表是配套的 ——
每个这样的词都要在术语表里标明词源,并给出它在各实现里对应的真实标识符
(见 `document-skeleton.md` 的术语表一节)。**只做前半条不做后半条,就是把认知成本转嫁给读者。**

横向对照表同理:**按不变量排行**。两代实现的 buffer 名完全不同,按名字排的表对不上;
按"同一个数学量的两种落法"排,差异一眼可见。

## 覆盖判据:样本选错,"一致"就是假象

横向对照给两种结论:**分歧处 = 设计自由度**,**一致处 = 硬约束**。
第一种结论只要样本真实就成立;**第二种结论依赖样本的多样性,而这一点很容易被忽略。**

实测教训:一次调研摆了三套实现,其中两套同源(一套基于另一套二次开发)。
"三套都要求序列长度被并行因子整除"看起来像该领域的硬约束。补进第四套非同源实现
(走完全不同技术栈的那一类)之后,这条立刻降级为"某类并行方式的约束",与该领域本身无关。
**同源样本会把上游的一个实现选择,伪装成领域的必然。**

三条固定动作:

**① 按设计自由度的取值选样本,不按"我能拉到哪几个仓"选。**
先列出你打算讨论的差异轴,再问每条轴:手上的样本覆盖了几个不同取值?
只有一个取值的轴,既不能证明它是自由度,也不能证明它是约束 —— 那条轴上你什么都没证明。

**② 把族谱写进材料。** 一句话即可:"A 与 B 同源,B 基于 A 二次开发;C 与 D 是独立实现。"
读者据此给"一致"打折。缺了这句,对比表会被当成 N 个独立证据。

**③ 覆盖不到的族要点名。** 写"XX 这一类没有覆盖,因为 YY",不要写"其他实现"。
点名的价值在于:读者一眼能看出你知道它存在 —— 这和"没想到"是两回事,
也让他能自己判断你的结论在他那一类上还成不成立。

判断样本够不够,有个简单的反问:**如果去掉其中任意一套,有没有哪条结论会塌?**
去掉谁都不影响的那些"额外样本",其实只是同一份证据的复印件。

## 从读者的困惑点找解释入口

困惑本身指示了解释该从哪切入。

例:被问"既然能原地改,为什么还要一块额外的临时区"。答案的关键是
**逐元素运算 vs 沿维度 reduce 的二分** —— 逐元素可以 src=dst 原地做;
但 reduce 的中间结果不能写回正在被 reduce 的那块内存。

所以解释**直接从这个二分讲起**,而不是继续罗列每个 buffer 装什么。
"罗列得更全"解决不了"没抓住区分点"。

配套手法:把**能证明这一点的那一行**贴出来。例如某个 API 的 workspace 大小是
tiling 函数的**入参** —— 这比"该 API 需要临时空间"这种泛泛说法有说服力得多。

## 降级 ≠ 删除

读者说某块内容"别处已经讲过了 / 作为附加例子简单说明就行",**不等于可以删干净**。

判据:**这块内容是不是前面某条主张的唯一证据?**

- 是 → **保留结论 + 指针**(留一句结论,细节指向另一节的行号/小节号),删掉展开的代码块
- 不是 → 可以删

两种可用的降级手法:
1. 某个案例的代码块删掉,但"它为什么必须存在"这条结论留下 + 指向专门讲它的那一节
   —— 因为这条结论是本节论点的支点,也是图上那条红色溢出条的解释
2. 一整批实物证据**整体下沉到最后一节**,正文每处留"手法见 §x"、"实物形态见 §x"
   —— 正文变轻,证据仍可回溯

**正文变轻的正确做法是加指针,不是砍证据。**

## 先立骨架,再补证据

需求方口述的结构就是骨架,**不要另起炉灶重排**。你的活是补证据。

证据的摆法:**每条数字紧跟在它支撑的那句主张后面**,而不是堆成一节让读者
自己找对应关系。

## 一条主线串起全篇

材料要有一条能一句话讲完的主线,每一节都挂在它上面。

好用的手法:**找到那条同时解释多件事的约束**。一个例子是"某个中间结果
装不进片上缓存"这一条 —— 它同时解释了旧一代为什么需要那个数学变换、
新一代为什么不需要、以及图上那条溢出条的意义。原先这三件事散在不同小节,
提为全节论点后串成一条因果链。

判据:**这一节的存在是不是被上一节逼出来的?** 是,就是因果链;
否则只是并列的知识点。

## 章节顺序:读者的依赖顺序,不是作者的发现顺序

**这是增量写作的系统性偏差,不是粗心。** 每次按反馈补内容时,新内容总被追加在末尾;
补了几轮之后,章节顺序就退化成了**你写它们的时间顺序**,而读者需要的是**依赖顺序**。

实测:一份材料的"全局视野"(一次完整流程的全景)是最后才补出来的,于是留在了 §1.3,
排在两节细节之后。需求方的反问一句话点破:"为什么全局视野放 1.3?"
—— 读者读细节时不知道自己在整条流的哪个位置,而这恰恰是全景要解决的问题。

判据对每一节问一次:

> **读者读这一节之前,必须先知道什么?** 答案在后面,顺序就错了。

有两类内容几乎永远在最前,而它们又几乎总是最后才写出来 —— 所以最容易排错:

| 内容 | 为什么必须最前 |
|---|---|
| 全局视野 / 一次完整流程的全景 | 所有细节都挂在它上面;没有它,读者读细节时不知道自己在哪 |
| 术语表 | 最小实例里就会用到那些词 |

固定动作:**每新增一节,回头问它该插在哪,而不是默认追加。**
重排的成本远低于让读者自己在脑子里重排。

## 交叉引用与顺序

- 重排小节后,**必须回去修所有前向引用**("下一页"→"后面两页"、"见 §2.3"→"见 §2.4")。
  改结构不改引用,是陈旧内容的另一种形式。**重排还会连带影响编号** ——
  编号的一致性检查见 `document-skeleton.md` 的"编号是命名空间"
- 硬件/背景介绍放在方法论之前 —— 方法论里的每条约束都要能指回背景
- 长文档给一个目录锚点

## 边界要写下来

材料只覆盖某一条路径时,明确写出未展开的分支(其他量化模式、其他数据布局)。
**"我没讲"和"我不知道"要区分开** —— 前者是范围选择,写出来读者就不会误以为你漏了。

选择性取材同理:agent 或源码里发现的差异点可能有十条,材料只取最能支撑当前论点的
四条,**并说明为什么只取这四条**(避免喧宾夺主),而不是全塞进去。
