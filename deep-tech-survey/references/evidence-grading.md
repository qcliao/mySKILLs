# 证据分级、hedge 纪律、取数通道

## 可信度分级

从低到高。**引用时必须知道自己站在哪一级。**

| 级别 | 来源 | 用法 |
|---|---|---|
| 最低 | subagent 的汇总表 / 二手转述 | **只当索引用**(告诉你去哪个文件哪一行),数值与层级归属一律回源码核 |
| 低 | 博客、非官方文档、模型记忆 | 补背景可以,不作为断言依据 |
| 中 | 论文、官方文档 | 骨架与出处可引;实现细节以源码为准 |
| 高 | **亲自 Read 过的源码**,带真实行号 | 可直接落笔 |
| 最高 | 亲自跑出来的数 | 可直接落笔,但要记录环境 |

**典型失效**:采信了 subagent 的数值汇总表,它把"切进下一级的中间粒度常量"当成了
那一级本身,导致三处硬伤同时落到材料里。熟悉代码的人一句"这个数肯定不对"就当场揭穿。

**教训**:agent 的数值汇总表要逐条回源码核对再落笔,尤其**层级归属**这类
——"这是不是它本身"比"这个数是多少"更容易错。

## 四种 hedge 处理

hedge 不是把话说软,是**把不确定性的类型标出来**。

**① 机制推断 → 标成推断。**
"A 因为没有某能力才选了这条路"——若官方文档只提到型号、未明说该能力缺失,
就在正文加注"此为机制推断"。结论可以留,因果要标。

**② 核不到的字段 → 不写。**
即使旁证很强也不写。例:专利的 assignee 从主题强烈指向某公司,但本地文本无该字段、
PDF 有权限锁 → 不落笔。**旁证强度不能替代字段存在。**

**③ runtime 值 → 只标注,不编造总数。**
`x = 1KB × preLoadNum` 这种运行期决定的量,图上标注表达式,不凑一个具体总量。

**④ 省略 → 显式标记。**
见下面的骨架代码手法。

## 骨架代码:删枝,而非改写

要在材料里放"看得懂的代码",做法是从真实源码**删枝**:

- 每一行都能在源码里定位,**行号一律用真实行号**
- 省略处统一写 `/*...*/`
- 删掉了分支要注明,例:"实际是按尺寸分桶的一串变体调用,此处只取其中一支,
  分支与量化参数已删" —— **不假装骨架就是全部**
- 不虚构 API 名、不合并两个真实函数成一个假函数

这样读者能拿着行号回源码验证,骨架就是可辩护的。

## 取数通道

**本地源码优先。** 手上有代码树就直接 Read,不要去网上找同一份代码 ——
版本可能不同,而你要讲的是手上这份。

### 联网取数时的仓库时效(实测踩过)

没有本地代码树时,"取到了"与"取对了"之间还差两步:

**① 锁 commit,不锁分支。** 材料里的行号只有配上 commit 才可核。
拉整树时也用 commit:

```bash
sha=$(curl -sSL "https://api.github.com/repos/<o>/<r>/commits?per_page=1" \
      | python3 -c "import sys,json;print(json.load(sys.stdin)[0]['sha'])")
curl -sSL "https://codeload.github.com/<o>/<r>/tar.gz/$sha" -o repo.tar.gz
```

整树比逐文件重要 —— **只有整树才能 grep 全部调用点**(SKILL.md 第二节),
而调用点不一致是最容易漏、也最容易被内行一眼看穿的一类错误。

**② 确认这个仓库还活着。** 这是实测中真正吃亏的一条:某仓的镜像可以正常访问、
目录齐全、文件能拉,但 HEAD 停在九个月前,内容是一条"本项目已迁移至别处"的通知;
活跃仓库里同一个文件已从 536 行变成 946 行。按镜像写完一整节后才发现,
所有行号必须重锚。

取数前的两个动作,成本几秒:

```bash
# HEAD 的日期与提交说明 —— 日期很旧或说明里出现"迁移/归档"就要警觉
curl -sSL ".../commits?per_page=1" | python3 -c "...['commit']['committer']['date']"
# README 头部常常就写着迁移声明
curl -sSL ".../raw/<sha>/README.md" | head -30
```

两个来源都能访问时,**逐文件比行数**,不同就以活跃的那个为准。

**③ 重锚之后必须重跑行号检查。** 换了代码树,行号会整体平移,
而平移后的行号往往仍然"存在"(不越界),只是指向了别的代码 ——
这种错误不会报错,只会让读者点开一看对不上。见 `verification.md` 的"行号引用回源"。

**④ 跨仓库的"同一个参数"要分别定位。** 同一个 API 在 A 仓已删除、B 仓仍在调用,
两件事同时成立 —— B 对齐的是 A 的旧版本。这不是矛盾,是两条时间线。
材料里要把两边都写出来,并说明各自的 commit。

**WebFetch 被拦时的绕法。** GitHub 的 HTML 页与 API 常被 WebFetch 拦,但这两个可通:

```bash
# 单文件原文
curl -sL https://raw.githubusercontent.com/<owner>/<repo>/<branch>/<path>

# 整仓文件树(先看结构再决定拉哪些)
curl -sL "https://api.github.com/repos/<owner>/<repo>/git/trees/<branch>?recursive=1"
```

raw 端点会**间歇 connection reset**,重试 2-3 次即可,不要因为一次失败就换方案。

**论文取原图与章节号。** WebFetch 论文页/博客拿图号与小节号,材料里连出处链接 ——
这样读者能自己去比对那张图。

## 落笔顺序

**先把事实核清,再动笔。** 省力的顺序是:派 agent 定位 → 自己 Read 关键处核对 →
落笔。费力的顺序是反过来:先按 agent 的汇总写完,再被指出错、整段重写。

两者的成本差一个量级,因为**错误一旦进入成稿就会扩散** —— 一个错的层级归属会牵连
正文、表格、配图标签、代码注释四处,改一处漏三处。
