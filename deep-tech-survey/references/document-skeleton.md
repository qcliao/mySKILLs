# 文档骨架:每一节由哪些部件构成

内容对不对是 survey 的事;**部件齐不齐是骨架的事**。一节缺了"代码对应"或"读法",
读者就得自己补那一跳 —— 大多数人补不上,于是就说"看不懂"。

## 标准节模板(五个部件,顺序固定)

一个讲清"某套实现怎么做某件事"的小节,按这个顺序摆:

```
① 一句话定位     这节要解决什么 / 承接上一节的哪个问题
② 领域模型        公式、阶段表、不变量 —— 先立锚,再谈实现
③ 执行流图        流程图 / 时序图 / 通路图,标出阶段编号 ①②③④
④ 代码对应        每个阶段贴真实代码骨架,带真实行号
⑤ 读法            把图和代码翻译成论点:所以差别在哪、为什么
```

**② 必须在 ④ 之前。** 先给公式/阶段编号,代码块里才能用 `═══ ① … ═══` 挂回去。
反过来先贴代码,读者得自己反推每段在算法里是哪一项(见 `material-anchoring.md`)。

**⑤ 不能省。** 图和代码只呈现事实,论点要显式写出来 —— 这是全篇最容易漏、
也最影响可读性的部件。

## ③ 执行流图:必须带阶段编号

图上的节点编号要和 ② 的阶段表、④ 的代码注释**用同一套编号**。这样三个部件互相锚定,
读者在任意一个部件里都能跳到另外两个。

```
flowchart LR
  A["① 门累积<br/>cumsum(log 域)"] --> B["② 求逆<br/>建 A 并就地求逆"]
  B --> C["③ 状态递推<br/>唯一串行的一段"] --> D["④ 求输出"]
```

节点里写**两行**:第一行是阶段名,第二行是这一步实际干的事(或关键约束)。
只写阶段名的图等于目录,没有信息量。

## ④ 代码对应:骨架 + 分隔注释 + 三类旁注

代码块不是贴源码,是**贴一条能读的执行流**。四条约定:

**用分隔注释把阶段切开**,编号与 ②③ 一致:

```python
# ═══ ① fla/ops/utils/cumsum.py —— 门累积,log 域 ═══
# grid (NT, B·H):每个 program 管一个 chunk 的一个 head
...
# ── Step 1:算 10 个 [16,16] 块,沿 K 方向 for 累加 ──
```

三级层次:`═══ 阶段 ═══` → `── 步骤 ──` → 行内注释。

**开头交代文件路径与函数名**,并注明这是"实测调用链"还是"结构示意"。

**三类旁注,各有固定标记:**

| 标记 | 用途 | 例 |
|---|---|---|
| `# grid (...)` | 并行维度 —— 读者最想知道"什么在并行" | `grid (⌈V/BV⌉, NT, B·HV):chunk 并行恢复` |
| `#@prec` 或 `# 精度:` | 这一步的数值精度(见 `output-forms.md` 的高亮机制) | `accum_dtype = "float32"` |
| `# 关键:` / `# ⚠` | 反直觉处、易误读处 | `⚠ 相邻两发看着一个禁 TF32、一个没禁,实际精度完全一样` |

`⚠` 专门留给**会被误读的地方** —— 用它标注"你可能以为 X,其实是 Y"。
这类旁注的价值最高,因为它拦住的是读者将要犯的错。

**代码里回指公式。** `# ↑ 这就是 §2.4.6 那条恒等式:log 域算差再 exp2,永不显式构造 1/γ`
—— 一行注释就把代码和公式缝上了。

## ⑤ 读法:每张图、每张表下面都要有

固定格式:引用块起头,`**图 N 读法**:`,然后**直接给论点**。

三种写法,按用途选:

**a. 单点论断** —— 图证明了什么
> **图 1 读法**:两代都把 L1 塞到 504KB/512KB(只剩 8KB),说明 **L1 就是硬约束**。
> **差别在分法**:一代囤住左矩阵、另一代把 84% 让给右矩阵轮转。

**b. 编号读法** —— 图有多个独立结论时
> 两个读法:① …;② 更有意思的是 …

**c. 一图多义** —— 同一张图同时是几样东西
> **图 9 读法**:这张图同时是四样东西 —— 保护点、实施例的量、从属权要的来源、
> 取证的抓手。

**读法必须回指前文。** 好的读法结尾都挂回某一节:"这正是 §1.1 架构图上那条
直连带来的连锁变化"、"§1.1 表里那一行的实际用途,就体现在这里"。

**修正也写在读法里。** 之前弄错过的数,在读法末尾用 `(⚠️ 修正:早前误把 X 当成 Y
—— 实际是 Z)` 标出来,不要静默改掉。读者可能看过旧版。

## 横向对比节的额外部件

对比 N 套实现时,在上面五件之外加三件:

**⑥ 统一视角先行。** 单独一个小节(如 `§x.0`)立"四个阶段、一条串行链"这类
统一框架,并明确"它们计算内容完全相同,不同的只有两件事"。**先说清什么相同,
再谈差异** —— 否则读者以为处处都不一样。

**⑦ 差异轴显式列出。** 不要让读者从对比表里自己归纳。写成"三类典型差异,
后面各节逐一展开:门在哪施加 / 精度选择 / 括号拆不拆"。

**⑧ 对比表按不变量排行**,不按各家变量名排(见 `material-anchoring.md`)。
表格列 = 各套实现,行 = 领域概念。

## 全篇骨架

```
标题
[[TOC]]                     长文档必须有(见 output-forms.md)
背景锚点                    为什么这件事和普通情况本质不同
├ 硬件/环境背景             约束的来源,必须在方法论之前
├ 总纲(方法论)            一张闭环图 + 由内而外的分步
├ 分步展开                  每步一节,用标准节模板
├ 例外处理                  常规方法盖不住时怎么办
├ 横向对比                  与另一范式/另一套实现对比
└ 验证与精度                怎么证明它是对的
```

两条硬顺序:
- **背景在方法论之前** —— 方法论里每条约束都要能指回背景
- **总纲在分步之前**,且分步的编号与总纲图一致

## 部件自查

落笔一节后过一遍:

- [ ] 这节的存在被上一节逼出来了吗?(因果链,不是并列知识点)
- [ ] 有领域模型(公式/阶段表)吗,还是直接上代码?
- [ ] 执行流图的编号与代码块的分隔注释一致吗?
- [ ] 代码块标了 grid / 精度 / ⚠ 三类旁注吗?
- [ ] 每张图表下面有读法吗?读法给了论点还是只复述图?
- [ ] 读法回指了前面哪一节?
- [ ] 未展开的分支写出来了吗?(见 `material-anchoring.md` 的"边界要写下来")
