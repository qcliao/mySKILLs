# 文档骨架:每一节由哪些部件构成

内容对不对是 survey 的事;**部件齐不齐是骨架的事**。一节缺了"代码对应"或"读法",
读者就得自己补那一跳 —— 大多数人补不上,于是就说"看不懂"。

## 标准节模板(五个部件,顺序固定)

一个讲清"某套实现怎么做某件事"的小节,按这个顺序摆:

```
① 一句话定位     这节要解决什么 / 承接上一节的哪个问题
② 领域模型        公式、阶段表、不变量 —— 先立锚,再谈实现
③ 执行流图        流程图 / 时序图 / 通路图,标出阶段编号 ①②③④
④ 代码对应        每个阶段贴真实代码骨架,带真实行号
⑤ 读法            把图和代码翻译成论点:所以差别在哪、为什么
```

**② 必须在 ④ 之前。** 先给公式/阶段编号,代码块里才能用 `═══ ① … ═══` 挂回去。
反过来先贴代码,读者得自己反推每段在算法里是哪一项(见 `material-anchoring.md`)。

**⑤ 不能省。** 图和代码只呈现事实,论点要显式写出来 —— 这是全篇最容易漏、
也最影响可读性的部件。

## ③ 执行流图:必须带阶段编号

图上的节点编号要和 ② 的阶段表、④ 的代码注释**用同一套编号**。这样三个部件互相锚定,
读者在任意一个部件里都能跳到另外两个。

```
flowchart LR
  A["① 门累积<br/>cumsum(log 域)"] --> B["② 求逆<br/>建 A 并就地求逆"]
  B --> C["③ 状态递推<br/>唯一串行的一段"] --> D["④ 求输出"]
```

节点里写**两行**:第一行是阶段名,第二行是这一步实际干的事(或关键约束)。
只写阶段名的图等于目录,没有信息量。

## 编号是命名空间,不是装饰

段号的唯一用途是**让读者在图、代码块、正文之间跳转**。所以它的要求比"看起来整齐"硬得多:

**一、一份材料的主干只有一套段号,所有者是那条主干**(计算流、主循环、算法阶段)。
同一个符号在两处指不同的东西,索引就失效 —— 而且**每一处单独看都自洽**,
只有把全文的编号并排列出来才会暴露。这与"同一个量三个名字"是同一类错误,
只是发生在编号上。

**二、不是主干上的一步,就不许占段号。** 判据一句话:

> 它是"主干上的一步",还是"关于主干的一个观察"?

后者(属性、实验、对照、附加说明)另开符号空间 —— A/B/C、甲乙丙、附 1 附 2。
实测中一份材料的主干是 12 段,却把"谁在训""优化器状态占多少""变长批次的浪费"
这些**关于**主干的实验也编进了段号,于是同一份材料出现两套 ①②③,
⑧ 一处指"损失"、一处指"语言模型前向"。改法是把 5 个实验移出段号,另编 A–E。

**三、允许多个命名空间,但每个都要声明所有者与作用域。** 长材料里合法地会有几套编号:
主干段号、某个函数内部的阶段号、读法里的枚举。规矩是**局部编号必须当场说明它是局部的**:

> 阶段划分……**这是一套局部编号**,只在本小节内有效,指 `_preprocess_data` 内部的六个阶段
> —— 与 §1.1 那条流的段号 ①–⑫ 无关,别把两处的 ⑥ 当成同一件事。

**四、编号出现在几个部件里,就要在几个部件里同时改。** 典型是五处:
正文小节标题、图上的节点/框标题、代码块的分隔注释、可运行 demo 的单元标题、跳转对照表。
改一处漏三处是这类错误的标准形态。

可测量的那一半:

```bash
python <skill>/scripts/check_numbering.py 材料.md demo/x.ipynb
```

它把每个编号的**定义处**(标题 / 表格单元格 / 代码注释)收集起来:
同一小节内一个编号绑定两个标签 → 硬失败;跨小节的那些列成一张表由人确认
"这是几个有意分开的命名空间,而不是几套指同一件事的编号"。
**机械可判的部分硬失败,需要人判的部分给表** —— 与行号回源那个脚本同一个分工。

## ④ 代码对应:骨架 + 分隔注释 + 三类旁注

代码块不是贴源码,是**贴一条能读的执行流**。四条约定:

**用分隔注释把阶段切开**,编号与 ②③ 一致:

```python
# ═══ ① fla/ops/utils/cumsum.py —— 门累积,log 域 ═══
# grid (NT, B·H):每个 program 管一个 chunk 的一个 head
...
# ── Step 1:算 10 个 [16,16] 块,沿 K 方向 for 累加 ──
```

三级层次:`═══ 阶段 ═══` → `── 步骤 ──` → 行内注释。

**开头交代文件路径与函数名**,并注明这是"实测调用链"还是"结构示意"。

**三类旁注,各有固定标记:**

| 标记 | 用途 | 例 |
|---|---|---|
| `# grid (...)` | 并行维度 —— 读者最想知道"什么在并行" | `grid (⌈V/BV⌉, NT, B·HV):chunk 并行恢复` |
| `#@prec` 或 `# 精度:` | 这一步的数值精度(见 `output-forms.md` 的高亮机制) | `accum_dtype = "float32"` |
| `# 关键:` / `# ⚠` | 反直觉处、易误读处 | `⚠ 相邻两发看着一个禁 TF32、一个没禁,实际精度完全一样` |

`⚠` 专门留给**会被误读的地方** —— 用它标注"你可能以为 X,其实是 Y"。
这类旁注的价值最高,因为它拦住的是读者将要犯的错。

**代码里回指公式。** `# ↑ 这就是 §2.4.6 那条恒等式:log 域算差再 exp2,永不显式构造 1/γ`
—— 一行注释就把代码和公式缝上了。

## ⑤ 读法:每张图、每张表下面都要有

固定格式:引用块起头,`**图 N 读法**:`,然后**直接给论点**。

三种写法,按用途选:

**a. 单点论断** —— 图证明了什么
> **图 1 读法**:两代都把 L1 塞到 504KB/512KB(只剩 8KB),说明 **L1 就是硬约束**。
> **差别在分法**:一代囤住左矩阵、另一代把 84% 让给右矩阵轮转。

**b. 编号读法** —— 图有多个独立结论时
> 两个读法:① …;② 更有意思的是 …

**c. 一图多义** —— 同一张图同时是几样东西
> **图 9 读法**:这张图同时是四样东西 —— 保护点、实施例的量、从属权要的来源、
> 取证的抓手。

**读法必须回指前文。** 好的读法结尾都挂回某一节:"这正是 §1.1 架构图上那条
直连带来的连锁变化"、"§1.1 表里那一行的实际用途,就体现在这里"。

**修正也写在读法里。** 之前弄错过的数,在读法末尾用 `(⚠️ 修正:早前误把 X 当成 Y
—— 实际是 Z)` 标出来,不要静默改掉。读者可能看过旧版。

## 全篇的第 0 个部件:最小完整实例

标准节模板解决的是"一节内部怎么摆",它解决不了这个问题:
**读者根本不知道这件事整体是怎么运转的,于是从第一节起就在猜。**

实测反馈的原话:"如果我都不知道这东西是怎么做的,我看这个就完全看不懂。"
这条反馈来自一份每个数值都有行号、结构完整的材料 —— 说明**可辩护性与可读性是两件事**,
把事实核准并不自动让人看懂。

补法不是加一段背景介绍(罗列名词只是换个地方让人猜),而是在任何分歧分析之前,
**把一个最小的完整实例从头走到尾**。三条判据:

- **具体到能对号入座。** 用真实常量,不用 N 和 M。"一张 448×448 的图,patch 14
  → 32×32 = 1024 个 patch → 经某步压成 256 个 token"比"图像被编码为若干 token"
  有用一个数量级 —— 读者能把自己的分辨率代进去算。
- **闭合。** 从输入一路走到最后那个标量(损失/输出),中间不留"这部分略过"。
  少一环,读者就得自己补,而他补不上才来看这份材料。
- **只有一条路径。** 最小实例里不出现分支、不出现"某些实现会…"。
  分支是后面各节的事;放进来它就不再最小,也就不再是锚点。

摆的位置:**背景锚点之后、总纲之前**。有了它,后面每节才能只讲"这一步各家怎么不同",
不必反复重述这一步在做什么。

### 最强形态:一个能跑的 demo,而且是 notebook

文字描述的最小实例已经有用,**能跑的更有用**:读者可以改一个数看会怎样,
而这正是"理解"发生的地方。形态上 notebook 优于脚本 —— 脚本一次打完所有输出,
notebook 能一格一格看形状怎么变,配图就在那一格下面。

**每一步三件套:公式 → 代码 → 图。** 只给图,读者不知道数是怎么来的;
只给代码,读者要自己在脑子里跑;只给公式,读者不知道它长什么样。
顺序与标准节模板一致:领域模型(公式)在代码之前,图在最后,再跟一句读法。
全篇的几条公式先集中列一遍,再分步展开。

正文里怎么用它(这份材料的做法,可照搬):

1. **给两种入口**:命令行版(一次看全)与 notebook(分阶段看),
   但**逻辑只写一次**,放进一个模块,两边都 import。
2. **把跑出来的输出贴进正文** —— 不是复述,是原样贴,并注明"这是打印的,不是我算的"。
3. **把 notebook 导出的图内联进产物**。图由代码生成,数字与正文自动一致;
   手画的图会在改动后悄悄过期。
4. **给两张桥表。** 一张把 demo 的每一步映射到真实源码的文件与行号;
   另一张写"这一步在真实系统里立刻变成什么问题 → 去哪一节"。
   前者让 demo 落地,后者让读者知道后面每节的目标 —— **少了后者,demo 就只是个玩具。**
5. **最后加一格"变一变"**:改掉一个输入参数,让读者看到哪些数跟着变。
   这一格通常是整个 demo 里信息量最大的。

**形状要带维度语义。** 打印 `[1024, 588]` 等于没说 —— 要写成
`(N_patch=1024, 3*P*P=588)`,并用一张小表说明每一维的含义与约束
(哪一维是序列长度、哪一维必须整除、哪一维在真实训练里大于 1)。
布局约定也要写:同一份材料里若既有 `[B,S,H]` 又有 `[S,B,H]`,
读者会在转置处彻底迷路。

一条容易忽略的:**图内文字受制于环境的字体。** 没有中文字体时,与其让标签渲染成方块,
不如图内用英文、说明写在图注里,并在材料里说明为什么 —— 这是可核验的取舍,不是将就。

配套一张图:最小实例的通路图。注意这张图通常**不承载尺寸语义**(它讲的是顺序与形状变化,
不是容量),所以图注里要写明"框的大小不承载信息",免得读者按 `diagram-as-claim.md`
第 3 条去解读它。

## 术语表:放在最小实例之前,一屏内

材料要自足 —— 读者不应当为了看懂它去别处查词。**判据很硬:正文里每一个
"不是日常汉语、也不是读者一定见过"的词,都要能在术语表里查到。**

实测反馈原话:"什么语言塔这些东西我就不知道是什么意思。"
这类词往往是写的人为了把 N 套实现统一起来而造的统称 —— 造得对,但没交代。

**三列固定,第三列是关键:**

| 术语 | 一句话定义 | 词源 / 在各实现里叫什么 |
|---|---|---|
| (领域词举例)视觉编码器 | 把图像变成一串向量的那个子网络 | 领域词:A 里是 `vision_model`,B 里是 `image_encoder`,C 里是 `visual` |
| (源码词举例)`grid_thw` | 一张图切成的 patch 网格尺寸 | 源码词,可直接 grep |
| (本文用语举例)吸收位置 | 本文用来给差异分类的框架 | **本文用语**,别处没有 |

三类词源必须标出来,因为读者对它们的动作不同:源码词可以 grep;领域词 grep 不到,
要看对照列;本文用语 grep 不到、别处也搜不到,只能回这张表。
**不标词源的术语表只解决了一半问题** —— 读者仍然不知道这个词能不能拿去问同事。

三条约定:

- **位置在最小完整实例之前**。最小实例里就会用到这些词,先给表,读者才不用往回翻。
- **只收正文真用到的词**。收了没用的词,表会变成词典;判据是"这个词在正文里出现过"。
- **同一个概念全篇只用一个词**。术语表存在的意义之一就是逼自己统一措辞 ——
  同一个东西一会儿叫"投影层"一会儿叫"适配器",读者会以为是两个东西。

## 横向对比节的额外部件

对比 N 套实现时,在上面五件之外加三件:

**⑥ 统一视角先行。** 单独一个小节(如 `§x.0`)立"四个阶段、一条串行链"这类
统一框架,并明确"它们计算内容完全相同,不同的只有两件事"。**先说清什么相同,
再谈差异** —— 否则读者以为处处都不一样。

**⑦ 差异轴显式列出。** 不要让读者从对比表里自己归纳。写成"三类典型差异,
后面各节逐一展开:门在哪施加 / 精度选择 / 括号拆不拆"。

**⑧ 对比表按不变量排行**,不按各家变量名排(见 `material-anchoring.md`)。
表格列 = 各套实现,行 = 领域概念。

**⑨ 样本族谱单列一段。** 对比表的读者会默认这 N 列是 N 个独立证据,
而它们经常不是 —— 其中几套可能同源。哪几套同源、谁是谁的下游,要显式写出来,
否则"N 套都这样"这个论断的分量会被高估(见 `material-anchoring.md` 的覆盖判据)。

## 全篇骨架

```
标题
[[TOC]]                     长文档必须有(见 output-forms.md)
背景锚点                    为什么这件事和普通情况本质不同
├ 硬件/环境背景             约束的来源,必须在方法论之前
├ 总纲(方法论)            一张闭环图 + 由内而外的分步
├ 分步展开                  每步一节,用标准节模板
├ 例外处理                  常规方法盖不住时怎么办
├ 横向对比                  与另一范式/另一套实现对比
└ 验证与精度                怎么证明它是对的
```

两条硬顺序:
- **背景在方法论之前** —— 方法论里每条约束都要能指回背景
- **总纲在分步之前**,且分步的编号与总纲图一致
