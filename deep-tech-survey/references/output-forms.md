# 产出形式:同一组断言的三种载体

形式不承载论证,但**形式会决定断言能不能被读到**。这一节是踩出来的排版经验,
和内容对错无关,只关乎"写对了但读者没看见"。

## 一份内容,三种载体,信息密度不同

| 载体 | 定位 | 密度 |
|---|---|---|
| **md** | 唯一事实源,所有内容的母本 | 最高,带全部行号与旁注 |
| **HTML** | **主产出** —— 别人真正读的就是这个 | 与 md 等同,加渲染(公式、流程图、目录) |
| **PPT** | 讲的时候用,一页一个断言 | 最低,每页只留结论 + 一张图 + 讲稿 |

**单向生成:md → HTML,md → PPT。** 绝不反向手改产出;要改就改 md 再重新生成
(陈旧产物是最高频的元错误,见 `verification.md`)。

**洞察再全面,产出不全面也等于没有。** 材料的可辩护性是必要条件,不是充分条件 ——
读者只接触产出。所以排版投入不是"锦上添花",它决定了那些核实过的断言
有没有真的到达读者。下面 HTML 一节给的是一份**验证过的基线**,可以直接照搬。

**PPT 不是 HTML 的压缩。** 页面上的密度上限比正文低一个量级。做法是
每页一条断言 + 支撑它的那一张图,细节全部下放到讲稿备注 —— 讲稿是
PPT 真正装内容的地方,正文只留钩子。

## 第 0 步:先试着装一个渲染器,再说"没有浏览器"

**这一条是自己踩出来的:我在同一份材料上写了好几轮"本环境没有浏览器,所以渲染核不了",
并据此设计了整条离线链路 —— 后来真去试,一条命令就装上了。**

```bash
npm i playwright && npx playwright install chromium && npx playwright install-deps chromium
```

三点值得记:

- **`install-deps` 是关键那一步**。Chromium 下载成功但起不来、报
  `libglib-2.0.so.0: cannot open shared object file`,不是装不了,是系统库没装。
  只看第一条命令失败就下结论"装不了",会得出错误的环境判断。
- **arm64 上要用 Playwright 而不是 Puppeteer**:Chrome for Testing 不发布 linux-arm64,
  Playwright 自己出 arm64 构建。`apt-get install chromium` 在很多镜像里也没有候选包。
- **下载大(约 200 MB),要放后台跑**,前台超时会让人误判成"装不上"。

**"环境没有 X"是一条断言,和材料里任何其它断言一样需要证据。**
写下它之前问一句:我试过几种装法?一种都没试,那句话就只是"我没试过"。

装上之后能做的事,离线断言替代不了 —— 见本文末尾"渲染回读抓到的五类故障"。

## 先判环境:生成链路和渲染器都不是白给的

下面那份样式基线默认"项目里已经有一条 md → HTML 的生成链路"。这个默认不总成立。
落笔前先确认三件事,答案不同,做法完全不同:

| 问题 | 是 | 否 |
|---|---|---|
| 项目里已有生成脚本? | 用它,别另起炉灶 | 自己写一个,并把它当交付物的一部分(读者要能重跑) |
| 能装依赖?(pip / npm 可达) | 可用现成 markdown 库 | 自己写转换器 —— 见本文"转换器的三个必踩坑" |
| **有浏览器可以看渲染结果?**(先按上一节试着装一个) | 可用 CDN 渲染公式与流程图,**但必须逐项在浏览器里数** | **不要把任何断言托付给 CDN** |

第三行是关键判据,实测中做过一次决策:环境里没有浏览器,于是**放弃 CDN 渲染的公式与
流程图,全部改成脚本生成的内联 SVG**,产物做成零外部依赖。理由不是"内联更好看",而是:

> 交给 CDN 渲染的东西,在这个环境里我核不了;而"核不了"不能当成"渲染正常"。
> 把可辩护性押在一条无法验证的渲染路径上,等于把"读者是否看到"变成未知数 ——
> 这正是本 skill 第一条铁律要消掉的那种未知。

代价是图要自己算坐标(见 `diagram-as-claim.md`),收益是**产物的每一条性质都能离线核**:
标签会不会被压(按字符分档估宽)、标签溢出数、`<svg>` 配平、外链资源数为 0。
有浏览器时不必这么做;没有时,这是唯一能把"渲染"从未知变成已知的办法。

自己写转换器时,顺手把这几项做成可计数的不变量(见 `verification.md`):
占位符残留 = 0、被转义的 `<svg` = 0、非法 `href` = 0、目录锚点悬空 = 0、
`<script>` 与外链样式表 = 0(自包含的证据)。

## HTML:一份验证过的样式基线

目标是**单文件自包含**(一个 .html 发出去就能看,图和公式在线渲染),
正文宽度收窄到 `max-width:920px` 居中 —— 全宽的行长在大屏上没法读。

```
body  920px 居中,padding 32px,line-height 1.7,色 #24292f
      font-family: -apple-system, "Segoe UI", "Microsoft YaHei", sans-serif
```

### 标题:相邻层级差"填充方式",不差色深

**典型失效:五级标题只靠深浅蓝区分,层级读不出来。** 改法是每级换一种填充:

| 级 | 字号 | 配色与装饰 |
|---|---|---|
| h1 | 2.6em | 深蓝字 `#052f6b` + **5px 下边框** `#0550ae` |
| h2 | 2.0em | **白字 + 实心主题蓝底 `#0550ae`** + 左侧 10px 深蓝竖条 `#032d60`,圆角 6px |
| h3 | 1.58em | 蓝字 `#0550ae` + **浅蓝底 `#eaf2fd`** + 左侧 7px 竖条 `#0969da` |
| h4 | 1.3em | 较深蓝字 `#0a58ca` + 左侧 4px 淡蓝竖条 `#7aa7e0`,**无底色** |
| h5 | 1.12em | 紫字 `#8250df`,**无底无条**(换色系,与 h3/h4 拉开) |

规律:**实心底 → 浅底 → 只有竖条 → 纯字**,四段填充强度单调递减;
`margin-top` 也逐级收(2.6em / 2em / 1.7em / 1.4em),视觉分组自然出来。

### 其余元素

```
code       浅灰底 #f6f8fa,圆角 4px,.9em,Cascadia Code / Consolas
pre        同底色,padding 14px,圆角 8px,overflow-x:auto
table      border-collapse,宽 100%,.92em;th 浅灰底;偶数行 #fafbfc 斑马纹
blockquote 左 4px 蓝条 + 浅灰底,字色调淡 #57606a
.figure    居中,svg 设 max-width:100%;height:auto(否则大图撑破正文)
.toc       浅灰底 + 细边框圆角盒,链接 display:block 逐行排
```

**表格斑马纹 + 表头底色**这两条对宽表可读性提升最明显,成本几乎为零。

### 精度标注:让它在代码块里跳出来

材料里要逐段标注数值精度时,**别写普通注释** —— 会淹在代码里。做法是约定一个
标记前缀,转换时整行套上高亮样式:

```python
# 源码块里写:    #@prec BF16 输入 / FP32 累加
m = re.match(r"^(\s*[│|]?\s*)(?:#|//)@prec\s*(.*)$", ln)
# → <span class="prec">精度 …</span>,保留前置缩进与树形符号
```

```
.prec  琥珀底 #fff3cd + 深橙字 #9a3412 + 粗体 + 左 4px 橙条 #d97706
```

这样精度标注在灰底代码块里是**唯一的暖色**,扫一眼就能找到所有精度切换点。
同时支持 `#` 与 `//` 两种注释符,并保留 `│` 这类树形前缀的缩进。

### 长文档必须有目录

`[[TOC]]` 标记 → 自动抓 h2–h4 生成锚点目录(标题渲染时给 `id="secN"`)。

**典型失效:转换脚本本来就支持,但从没在文档里放过标记。**
教训:**功能存在不等于被使用** —— 写长材料前先把生成链路支持的能力过一遍。

### 转换器的三个必踩坑

这三个都出过事,而且都是"治本"而非改措辞(见 `verification.md`):

**① 需要原样透传的内容必须先 stash 再还原。** 代码块、内联 SVG、数学公式都要先
替换成占位符,处理完 markdown 再插回 —— 否则转义会把 `<svg>` 变成纯文本、
把公式里的 `<` 打断。**占位符残留数必须验证为 0。**

**② 公式 stash 的顺序:先 `$$…$$` 再 `$…$`**,且用非贪婪匹配保证定界符成对。
反了会把 display 公式切成两个 inline。

**③ 链接正则不能写成 `\[(.*?)\]\((.*?)\)`。** 它会把正文里"`]` 紧跟 `(`"的普通文字
当成链接(容易受害的是这类句子: `…[2-3](softmax(t0)←…`)。
收紧 URL 部分到真实 URL 字符集:

```python
r"\[([^\]]*?)\]\((https?://[^\s()]+|[#./][^\s()]*)\)"
```

图片正则要单独放在链接之前处理,否则 `./x.png` 这类相对路径会被吃掉。

### 浏览器实测清单

CDN 渲染的东西**必须在浏览器里数**,不能只看生成成功:

- 公式:表达式计数 > 0、`.katex-error` = **0**、正文残留 `$` = **0**
- 流程图:图数符合预期、渲染报错 = **0**
- SVG:`<svg>` 与 `</svg>` 配平、被转义的 `&lt;svg` = **0**、`.figure` 数一致
- 代码块横向溢出:`scrollWidth > clientWidth`,新增块一律不许溢出,
  已有的记下基线不让变多
- 非法 `<a href>` = **0**(链接正则的回归项)
- 逐屏截图肉眼看一遍

## PPT:自适应字号与溢出预测

没有渲染器可查时(纯脚本生成 pptx),文字会不会被裁只能**估**。
这套估算器踩出过一次"某页文字没显示出来",根因不在那页内容,在估算器本身。

**① 逐字符分档估宽,不能一律一个系数。**
中文字体下大写字母与数字明显比小写宽。全按小写算,会把大写密集的行
(缩写、类名、全大写术语)低估到"不换行",于是少算一行、文字被挤出文本框。
一组可用的 em 系数:CJK 全角 1.0、大写与数字 0.62、小写与符号 0.52、空格 0.30。

**② 三道余量各有职责,互相不能吞掉。** 这是文字被裁最常见的真正原因:

| 余量 | 位置 | 吸收什么 |
|---|---|---|
| 宽度 ~7% | 估行数时 | 字距、标点压缩(逐字加和的固有误差,约 ±5%) |
| 高度 ~8% | 选字号时 | 估错一行的高度 |
| 富余只摊 80% | 分配剩余空白时 | **必须留白**,全摊掉则排版高度正好等于可用高度 |

第三道被吞掉时,前两道就白留了 —— 排版高度恰好等于上限,**任何一行估错立刻被裁**。

**③ 二阶诊断:报"贴边行",不只报"溢出"。**
估算值落在真实箱宽整数倍附近 ±5% 的行,行数可能算错一行 —— 这些是下一个 bug 的
预备役。把它们列出来(页号 + 倍数 + 文本),建议改短,而不是赌估算准。

**④ 检查脚本必须枚举所有版式。** 漏检往往因为脚本只覆盖了其中一种版式,
而出事的页是另一种。判据要**照抄真实排版代码里的常量**,不凭记忆写。

**⑤ 图片有效 PPI 要在区间内。** 太低模糊,太高白占体积。落在
150–330 之外的图列出来复核。

## 图文同放与页序

- 时序图/流程图紧贴对应代码,不集中成一节(读者看图时能对着代码验)
- 页序排成因果链:**这一页的存在被上一页逼出来**
- **重排后必须回去修前向引用**("下一页" → "后面两页")—— 改序不改引用,
  是陈旧内容的另一种形式

## 生成前的固定动作

1. 目标文件**没被打开占用**(被锁时可能静默只写出一部分,却不报错)
2. 生成后核对**字节数/页数变了**,且变化量能解释
3. 在产出里 grep 本次新增的关键串,确认真的进去了
4. 结构计数符合预期增量(见 `verification.md`)
5. 渲染出来逐屏看一遍 —— 计数全对也可能排版崩


## 渲染回读抓到的五类故障(离线断言全都没抓到)

同一份材料,结构计数全绿、引用全部回源、图的标签溢出为 0 —— 装上浏览器逐屏读回之后,
仍抓到五类故障。**它们的共同点是:每一类在源文件层面都看不出来。**

| 故障 | 为什么离线抓不到 | 治本改法 |
|---|---|---|
| 中文跨行处被插入空格("机制 都建立在") | md 里是两行,拼接时无条件插了空格;纯文本比对看不出多了一个空格 | 拼接段落时**CJK 边界不插空格** |
| 图例压在最后一行节点上 | 几何检查只查了"节点两两不重叠" | 把**游离文字 vs 节点**也纳入断言 |
| 回边标签压进节点框 | 同上 | 回边改走网格下方的**专用通道** |
| 连线穿过第三个节点 | 节点不重叠、文字不压节点两条都过 | 把**边 vs 节点**也纳入断言 |
| 六列对照表被容器裁掉 | `overflow-x:auto` 让它能滚,计数与配平全部正常 | 长路径移出单元格做脚注 + `overflow-wrap:anywhere` |

规律很清楚:**几何断言替代不了目检,但目检发现的每一类故障都能固化成新的断言。**
上面那张表里三条"图"的故障是同一个循环跑了三遍:看图 → 发现一类新故障 → 写成断言 → 再看图。
到第三遍才没有新故障。**第一遍就宣布"几何检查通过"是不够的 —— 断言的覆盖面本身要靠目检来长。**

还有一条**语义**故障,更值得记:因果掩码图上那条标注"vision starts"的竖线画在 `PROMPT_LEN=19`,
而视觉段是 0–255,19 在它内部 —— **那条线什么也不标**。这不是排版问题,是图上的一条错误断言
(`diagram-as-claim.md` 第一句)。它躲过了所有离线检查,因为脚本不知道那条线**应该**在哪。
**图上每一条标注线都要回答"它标的那个位置是怎么算出来的"** —— 答不出,就是装饰。
