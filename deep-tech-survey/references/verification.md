# 验证:结构不变量、精度基线、陈旧产物

## 不看"生成成功",看结构计数

"脚本跑通了"不是验证。**验证 = 结构计数符合预期增量。**

每轮改动前先想清楚每个计数**应该**变成多少,再去数:

| 计数项 | 预期 |
|---|---|
| 图/表/代码块个数 | 明确的增量,例:表 13 → 15(新增 2 张) |
| 净增量要能算清 | 例:`<pre>` 21 → 25(删 1 加 2、删 1 加 2 = 净 +4) |
| 公式渲染错误 | 必须 **0** |
| 转义泄漏(该原样透传的标签被转义) | 必须 **0** |
| 开闭标签配平 | `<svg>` 与 `</svg>` 数量相等 |
| 占位符残留 | 必须 **0**(替换式流水线的典型漏洞) |
| 非法链接 | 必须 **0**(见下"治本") |
| 正文残留公式定界符 | 必须 **0** |
| 横向溢出 | 代码块 `scrollWidth > clientWidth` |

**字节数当变更证据。** 记录改前改后的字节数,差值要能解释。
例:某次移动图片目录后 HTML 从 359189 → 359203,差 14 字节 = 2 × `len("assets/")`
—— 差值算得清,就证明改动范围正是预期的那些。

**新串在位检查。** 本次新增的关键标识符逐个 grep 计数;同时确认旧的错误串已消失。

**渲染后肉眼看。** 计数全对也可能排版崩(文字被线穿、标签越界)。
逐屏截图看一遍,这是唯一能发现布局问题的手段。

## 行号引用回源:数值有 grep 兜底,行号没有

写错一个数,内行一眼看出"这个数不对";写错三行行号,**没有任何症状** ——
文字通顺、格式正确、看起来完全可信,只有读者真去点开那一行才会发现对不上。
这是深度材料里唯一一类"错了也没人当场发现、但一旦被发现就整篇失信"的错误。

实测:一份材料 130 多条 `文件:行号` 引用,自认为逐条核过,脚本扫出来仍有 4 条偏移 1–3 行
(都是"函数体第一行"与"函数定义行"之类的错位),另有 2 条在换代码树版本后指向了别的代码。

```bash
python <skill>/scripts/check_refs.py 材料.md --root <代码树根>
```

脚本做三件事,都是机械的:

| 检查 | 抓什么 |
|---|---|
| 文件存在 | 路径写错、文件被移动 |
| 行号不越界、区间端点合法 | 换版本后文件变短 |
| 短名引用有唯一候选 | `train.py:308` 这类简写在多个目录里都有同名文件 |

**脚本判定不了"该行内容是否支撑正文"** —— 所以它的主要输出不是通过/失败,
而是一张"引用 → 该行真实内容"的并排表,人扫一遍。130 条扫下来约两分钟,
而且**只有这一步能发现"行号存在但指错了地方"**。

配套约定:**每个文件在正文里至少出现一次完整路径**,之后才允许用短名引用。
这既是给读者的(短名歧义),也是给脚本的(短名靠这条规则解析)。

## 贴进正文的程序输出,要能重跑比对

材料里贴 demo 的输出、跑出来的表、命令的回显 —— 贴进去的那一刻,
它就从"程序打印的东西"变成了"我写的字"。**改了程序忘了改正文,不会有任何症状。**
这与"改了源文件忘了重新生成产物"是同一类失败,所以用同一种办法处理。

项目内写一个小脚本,做三件事(具体形态因项目而异,思路通用):

| 检查 | 做法 |
|---|---|
| 程序还能跑 | 子进程跑一遍,退出码必须为 0 |
| 正文里的关键数值来自这次运行 | 从输出里正则抓关键数字,逐个 `in` 正文 |
| 正文里贴的形状串没有过期 | 把正文里的 `[1, 305, 320]` 这类串拿去输出里找 |

notebook 另有一条独立的检查(是否完整执行过),用通用脚本:

```bash
python <skill>/scripts/check_notebook.py demo/x.ipynb
```

**实测有效**:一次改动把 demo 的输入从随机噪声换成合成图案,形状全部不变、
所有结构计数照常通过,只有损失值与梯度范数变了 —— 正文里贴的旧数值靠这条检查才被抓出来。

## 陈旧产物:最高频的元错误

**源文件改对了,但没重新生成产物 —— 读者看到的还是旧的。**

典型场景:一批反馈里的多数条目其实早已落到源文件,但产物没重建,
于是同一批问题被再提一次 —— 而你困惑"这不是已经改了吗"。**争论之前先看产物。**

固定动作:
1. 改完源文件 **立刻重新生成**
2. 生成前确认目标文件**没被占用**(被编辑器/播放器锁住时,某次只写出 40 页而非全部,
   却没有报错)
3. 生成后**核对字节数变了**
4. 在产物里 grep 新内容,确认真的进去了

对应全局原则:**self-written claims are not evidence — check the artifact.**
"已修改 X"只在有工具调用背书时才能这么写。

## 治本不治标

同一类问题第二次出现时,改产生它的机制。

例:正文里出现了一个无效链接。看着像笔误,实际是转换脚本的链接正则
`\[(.*?)\]\((.*?)\)` 太宽松,把正文里"`]` 紧跟 `(`"的普通文字当成了 markdown 链接
—— 全文两处受害,且都在同一类句式里。

**修法:收紧正则到真实 URL 字符集,而不是改正文措辞躲开它。**
改措辞能让这两处消失,但下次写出同样句式还会中招。

配套:修完加一条**回归检查**(非法链接计数 = 0),让这类问题从此可测量。

## 检查脚本必须枚举全部变体

自动检查只覆盖一部分情况时,漏掉的那部分就是下一个 bug 的藏身处。

典型失效:一个排版检查脚本只检查了其中一种版式,而出问题的页面用的是另一种版式
—— 于是问题一路走到读者眼前。

固定动作:写检查脚本时**枚举所有变体**,并对每个变体确认判据与真实排版代码一致
(照抄常量,不凭记忆写)。

## 精度:等价性是数学的,差异是精度的

多阶段数值计算的材料里,**逐段标出精度自由度,并指出哪些段没有自由度**。

核实过的一组数支撑这句话:高精度下两种数学等价形式的相对误差是机器精度量级;
降到低精度后,两种形式的误差**同等大小** —— 差异来自精度,**不是来自形式变换**。

由此得到的实操推论,适用于任何数值验证:

**① 基线必须同精度。** 拿高精度参考实现当标杆,会把低精度的**既定损失**误判成 bug。
同类错误:标杆本该在目标设备上算,却图省事在 CPU 上算,位宽更高,于是被测方
显得"不过关"。

**别把某一个实现当"真值"。** 常见误解是"递推版是标准答案,并行版偏离了它"。
实际上两者都是被测对象、都与一个更高精度的参考实现比,各有自己的容差
(典型是并行版容差略大,因为多了一层块内变换)。**先去看仓库测试里的容差是多少、
比的是谁** —— 这比自己猜哪个更准可靠得多。

**② 配置可能被静默忽略。** 写下"我关了某个低精度模式"之前,确认它在当前
dtype 与代码路径下真的生效 —— 某个精度开关会因为输入本身已是低精度而完全无效。

**③ 溢出不是精度档位能解决的。** 若几个精度档位的指数位宽相同,换档位不解决溢出;
解决办法是让危险的量**只以比值形式出现**,并确认存在配对源与配对所需的次序保证。

**④ 数据构造的两难要写出来。** 随机+均匀分布往往不合理;从真实网络抓输入又有
"选哪个模型/数据集/够不够 general"的问题。测试本身有随机性 → 多次采样综合看。

## 精度标注怎么落到材料里

按阶段列表:每段用什么精度、**为什么这段没有自由度**、哪段是精度敏感的关键路径。
判据一句话:**这个量会不会被反复乘进自己?** 会 → 必须保高精度;不会 → 可以降。
