# 写可辩护的技术材料

**核心原则:材料里每一条断言都要能追到一个你亲自核过的事实,而读者看到的是产物、不是源文件。**

**动手顺序**:接到"调研一下 X"时,**先做范围勘察并把选择摆给需求方**(见"两个阶段"一节),
范围定了再进入下面的核实纪律。跳过这一步,做得再准也可能整节返工。

## 一、读者读的是产物,不是你改的那个文件

材料通常由 md 生成 HTML/PDF/PPT。这里有一个几乎无法自查的失败:**你改对了源文件,
产物却没重新生成** —— 于是读者还在看旧内容,而"我改好了"的感觉和"读者看到了"之间
没有任何东西会提醒你。实测中一个 agent 甚至在报告里推理了 HTML 的渲染结果,
却从头到尾没生成过它。

所以改完源文件、报告完成之前,跑一次生成 + 核对:

```bash
python build_html.py                 # 或该项目的生成命令

python <skill>/scripts/check_artifact.py 材料.md 材料.html \
    --expect "本次新增的串" --gone "本次删掉的串"
```

`check_artifact.py` 一次核三件事:产物 mtime 新于源文件、新串在两边都命中、
旧串在两边都消失。退出码非 0 就是不同步,别在这种状态下说完成。
(手工等价物:`grep -c` 两个文件 + `stat -c '%y %n'`。)

**项目里没有生成链路怎么办** —— 自己写一条,并把它当交付物的一部分(读者要能重跑)。
装不了依赖、没有浏览器时的取舍见 `references/output-forms.md` 开头那张判定表:
核心是**不要把断言托付给一条你无法验证的渲染路径**。

几个容易说服自己跳过的情形,其实都不成立:改动只有一个词、生成脚本没动过、
"我知道它会渲染成什么样"。前两个与产物是否过期无关,第三个是**推理**而非**生成**。

两点补充:

- **生成前确认目标文件没被程序占用**。被 PowerPoint / 编辑器锁住时,可能静默
  只写出一部分而不报错 —— 于是你拿到一个页数不全却看起来正常的产物。
- **回退改动时也要再生成一次**。试验、走错方向、需求变更导致源文件回退后,
  如果不重新生成,留下的是"产物比源文件新、内容却对不上"的更隐蔽的不一致。

**"已修改 X"只在有工具调用背书时才写得出来**,否则写"待生成"。

## 二、数值、层级、调用位置,只能来自你亲自读过的源码

论文、同事口述、subagent 汇总表 —— 这三者是**索引**,告诉你去哪个文件哪一行,
而不是可以直接落笔的事实。它们出错的方式很一致:细节对了,但**归属**错了。

所以最容易翻车的不是"这个数是多少",而是**"这个数是什么"**:

| 陷阱 | 具体表现 |
|---|---|
| 层级归属 | 把"切进下一级的粒度"当成"这一级本身",二者常差几倍 |
| 调用位置 | 把只在 backward 调的函数画进 forward 流程 |
| 切分用途 | 混淆"为并行而切""为装进下级存储而切""为搬运而切" |
| 签名漂移 | 返回值个数、常量按版本/硬件分叉 |
| 配置失效 | 精度开关因输入已是低精度而被静默忽略 |

**落笔前 grep 一次**:函数的所有调用点、常量的所有定义处。别看名字猜 ——
名字最像"就是那个东西"的时候恰恰最危险。

**还要问一句:它属于哪条执行路径?** 实测中两处翻车都是这样来的 ——
用 `class Inference` 里的一个常量论证**训练**侧的尺寸;
用只被采样循环调用的函数论证**训练**时的整除性质。
文件对、行号对、函数确实存在,**但那是另一条路径上的代码**。
所以行号校验实际有四层:**文件存在 → 行号不越界 → 落在哪个定义里 → 那个定义在哪条路径上**。
前三层机械可判(见第四节),第四层只能靠 grep 调用点。

**"没有 X"这类全称否定,写之前先 grep 一遍 X。**
实测中一轮就被推翻三条,每条都在同一份代码的另一个分支里。

一个具体的样子:

> 转述:"这个 kernel 的分块是 128。"
> 回源码:`128` 是切进下一级存储的粒度,这一级实际是 `512`,注释里写着 `512/128`。
> 落笔:`SingleN=512`,并注明 `128` 是切进 L1 的粒度 —— 两个数都留下,读者不会再误读。

写进材料的形态是"**值 + 它是什么 + 出处**",三者缺一就还没核完。

**从配置文件里取的数,还要自己算一遍导出量。** 配置里的数是**原料**,不是结论。
只读它们,读到的是设计者的意图轮廓,而意图与实际效果可以差很远。

实测中曾把一组"随参数单调下降"的配置读成"在做均衡",算出乘积后发现两端相差 4.5 倍。

**固定动作:配置里的每组数,至少算一个导出量(乘积、比值、极值)再下判断**,
并把这个计算放进 demo —— 它同时成了可复核的实证。

**常量的名字是作者的说法,不是它的语义。** 同一轮里我把一个叫
`AE_SPATIAL_COMPRESSION` 的常量当成了自编码器的空间压缩率,据此推出"某些尺寸切不动"。
去读它**被用在哪里**才发现它是"压缩率 × patch"的合并步长,而且调用处用 `ceil`
保证了整除。**要判断一个常量是什么,看它的使用点,不看它的名字。**

## 三、代码是从网上取的时候,先确认它是不是现状

没有本地代码树时才联网取。这时**版本对不对**分两层,第二层是实测踩过的:

1. **锁 commit,不锁分支** —— 分支会漂移,读者按你写的行号就核不到。
2. **确认这个仓库还活着** —— 镜像能打开不等于镜像是现状。实测中一个仓的镜像可以正常
   访问、文件齐全,但 HEAD 停在九个月前,内容是一条"已迁移至别处"的通知;
   活跃仓库里同一个文件已经从 536 行长到 946 行。按镜像写完一整节后才发现,只能重来。

固定动作:取数前看一眼 **HEAD 的日期**与 **README 头部有没有迁移声明**;
两个来源都能访问时,逐文件比对行数,不同就以活跃的那个为准,并在材料里写明哪个是哪个。

3. **确认它有你要的那部分** —— 活跃、知名、星标高,都不代表它包含你要写的那条路径。
   实测中一个 17k 星的视频生成仓通过了前两条检查,但它顶层只有 `generate.py`,
   **全树 grep 不到任何 `train` / `finetune` 路径 —— 它是推理仓**。
   按"活跃且知名"选进样本,会读到写不出东西才发现。

   判据一句话:**把你要写的那一节的动词,拿去 grep 仓库的路径。**
   写训练就 grep `train`,写调度就 grep `schedul`,一条都没有就换候选。
   成本是一条命令。筛掉的候选要写进材料的"未覆盖",并说明筛掉的理由 ——
   读者会问"为什么没有它"。

**跨仓库的"同一个参数"要分别定位。** 同一个 API 在 A 仓已删除、在 B 仓仍在调用,
两件事可以同时成立 —— B 对齐的是 A 的旧版本。答案取决于问的是哪个仓的哪个 commit,
所以材料开头就要有一张"仓库 + commit + 日期"的表。

## 四、行号会漂,要有机制而不是靠细心

数值有 `grep` 兜底,**行号没有** —— 写错三行照样能编译、照样看起来像真的,
只有读者点开那一行才会发现对不上。实测中一次调研写了 130 多条 `文件:行号` 引用,
人工复核后仍有 4 条偏移 1–3 行,全部是脚本扫出来的。

做法是让脚本把"正文写的行号"与"该行的真实内容"并排打出来,人只负责扫一眼:

```bash
python <skill>/scripts/check_refs.py 材料.md --root <代码树根>
```

它能判定:文件存在、行号不越界、区间端点合法、短名引用是否有唯一候选。

**还差一层:行号落在哪个定义里。** 实测中两条引用通过了上面全部检查,却指向了别的函数
("损失的实现见 `x.py:263-270`",实际落在 `param_groups` 里)。
做法是从源码解析出顶层定义的行号区间,对每条引用报出**所属定义名**,
并对"从某个定义的中间切起"硬失败。细节见 `references/verification.md` 的三层表。
**自带 demo 的材料尤其要做这一层** —— demo 改得勤,正文里的引用不会跟着动。
它**判定不了**该行内容是否支撑正文 —— 这一项必须人看,但有了并排输出,
扫 130 条只要两分钟。重锚版本(见第三节)之后必须重跑一次:行号会整体平移。

## 五、覆盖面不够时,"一致"是假象

横向对照的两种结论里,**"一致处 = 硬约束"这一条只有在样本跨了实现族谱时才成立。**

实测教训:一次调研摆了三套实现,其中两套同源(一套基于另一套二次开发),
"三套都要求序列长度被并行因子整除"看起来像多模态的硬约束。补进第四套非同源实现
(不用多维并行的那一类)后,这条立刻降级成"多维并行的约束",与多模态本身无关。
**同源样本会把上游的实现选择伪装成领域的必然。**

三条固定动作:

- **按设计自由度的取值选样本,不按"我能拉到哪几个仓"选。** 每条差异轴至少要有
  两个不同取值,否则那条轴既不能证明是自由度,也不能证明是约束。
- **把族谱写进材料**:哪几套同源、谁是谁的下游、谁是独立实现。读者据此判断"一致"的分量。
- **覆盖不到的族要点名**:写"XX 这一类没覆盖,因为 YY",而不是"其他实现"。

## 六、最具象的解释是一个能跑的 demo

深度材料默认读者已经知道这件事整体怎么运转,而这个默认经常不成立。
补法不是加一段背景介绍(那只是换个地方罗列名词),而是**在分歧分析之前,
先把一个最小的完整实例从头走到尾**;而实例的最强形态是**一段真能跑的代码**。

**这是全篇性价比最高的一段**:后面每一节都在讲"这一步各家怎么不同",
而"这一步是什么"只在 demo 里讲一次 —— 它错一分,后面每节都跟着错一分。
按主干投入,不是收尾时补个附录。

### 验收标准是读者能上手

三个问题,答不出就是没达标:

| 验收问题 | 不达标的样子 |
|---|---|
| 读者能说出**每个数是怎么来的**吗 | 只报结果,不给公式,也不给算出它的那行代码 |
| 读者能**改一个参数并预测结果**吗 | 没有"变一变"那一格 |
| 读者能**在真实仓库里找到对应位置**吗 | demo 与源码之间没有映射表 |

还有一条更硬的:**把 demo 单独发给没读过材料的人,他能不能靠它入门?**

### 回路要闭到题目上

**判据是一句反问:题目里那个名词,在 demo 里有对应的代码吗?**

材料叫"训练框架",demo 就必须真的训练。只跑到"前向 + 一次反向"看起来很完整,
但参数怎么更新、谁在训谁冻着、优化器状态占多少、批次形状不齐怎么办,一个都没出现 ——
**这样的 demo 讲的其实是数据预处理**,而读者会以为那就是全部。

| 题目是 | demo 至少要跑到 | 只跑到这里就是跑偏 |
|---|---|---|
| 训练框架 | 参数分组与冻结、优化器状态、多步更新、批次组织 | 前向 + 反向 |
| 推理引擎 | 缓存的分配与复用、批次调度、采样 | 单条前向 |
| 数据管线 | 落盘格式、乱序与恢复、多进程切分 | 单条样本的变换 |
| 某个算子 | 与参考实现的数值比对、边界形状 | 跑通一次调用 |

**"能不能过拟合一个固定小批"是训练类 demo 的标准冒烟测试** ——
每步换随机样本时 loss 也会抖,但那证明不了接线正确。

### 位置与构成

- **放在最前面,并且只放一个。** 后面各节不再重复"这一步是干什么的"。
  每节都塞一个小 demo 会把主线切碎。
- **它要能承重**:后面所有细节都挂在它上面,所以必须穷尽整条主干,一步都不能省。
- **不是任何一套实现的简化版**,而是 N 套实现**共有的那条骨架**:
  少一步跑不通,多一步就不再是各家共有的。并行、精度、拓扑这些差异全部拿掉。
- **每一步三件套:公式 → 代码 → 图。** 三样各回答一个不同的问题
  (这个数**是什么** / **怎么算出来的** / **长什么样**),缺任何一样读者都要自己补那一跳。
- **形态上 notebook 优先**:脚本一次打完所有输出,notebook 能一格一格看形状怎么变。
- **末尾加一张桥表**:"这一步 → 它在真实系统里立刻变成什么问题 → 去哪一节"。
  **判据:读完 demo,读者能不能说出后面每节要解决的是哪一环?**

### 反模式:轻描淡写

出现任何一种就是没达标:

- 只给结论不给中间量;形状不带语义;跑到一半就停
- 图没有代码、代码没有出处
- **一次只补一点** —— 每轮反馈只加一小块,看起来在推进,实际每轮都没达到验收标准。
  **判据不满足时应当重做那一节,而不是打补丁。**

### demo 与材料之间要有校验

demo 是自己写的、改得勤,而正文里对它的引用不会跟着动。所以:
贴进正文的输出要能重跑比对,贴进正文的代码要与源文件逐字一致,
引用它的行号要能报出所属定义。细节见 `references/verification.md`。

## 两个阶段:先勘察并反问,再深入核实

**"调研一下 X"是一句范围未定的需求。** 直接挑几套实现深入,等于替需求方做了他没做的决定 ——
而这个决定通常是错的:实测中一份调研深挖了三套实现、每条断言都可核,交付后第一反应是
"torch 原生那一套呢?"。**深度做满了,范围没对上,返工的是整节。**

所以分两个阶段,中间有一个**必须停下来问人的点**。

### 阶段一:范围勘察(浅、快、不下结论)

目标不是回答问题,是**把选择摆到需求方面前**。产出四样东西,加起来控制在一屏内:

| 产出 | 内容 | 判据 |
|---|---|---|
| 候选清单 | 有哪些实现/方案,**按族谱分组并标血缘** | 同源的要合并成一组,别当成多个候选 |
| 差异轴清单 | 打算比什么(不是"比一比",是具体的轴) | 每条轴要能说出"取值可能有哪几种" |
| 取数成本 | 每个候选:代码能不能拿到、有没有官方文档 | 拿不到的要现在说,不要写到一半才发现 |
| **待确认问题** | 3–5 个,**每个都要影响后续做什么** | 答案不改变工作内容的问题,不要问 |

勘察阶段**不读实现细节、不记行号**。这一阶段的错误成本是几分钟,深入之后是整节。

### 收敛点:哪些必须问,哪些自己定

问不问的判据只有一条:**不同答案会不会导致做的事不一样。**

| 必须问 | 自己定 |
|---|---|
| 覆盖哪些族(以及明确排除哪些) | 每套实现从哪个文件读起 |
| 深度优先(2 套挖透)还是广度优先(6 套各摸一层) | 用什么图、几张图 |
| 读者是谁(决定要不要术语表、最小实例的起点) | 章节怎么分 |
| 有没有必须落地的目标栈(决定哪套是主角) | 用哪些校验脚本 |

把问题连同**你的默认选项**一起给出("不指定的话我按 A 做"),需求方点头即可,不必逐条回答。

### 阶段二:深入核实(四步主循环)

范围确认之后才开始,这时才谈行号。

| 步 | 做什么 | 产出 |
|---|---|---|
| ① 论文 | 拿骨架 + 可引用坐标(章节号/图号) | 阶段表、权威出处链接 |
| ② 源码 | 逐条核对 ① 的先验 | **校正清单** —— 差异本身就是产出 |
| ③ 横向对照 | N 套实现摆一起,**且 N 要跨族谱**(第五节) | 分歧处 = 设计自由度,一致处 = 硬约束 |
| ④ 反推 | 用容量/带宽约束反解常量 | 把陈述变推导 |

**范围在阶段二中途变了,要回到收敛点重新确认**,而不是顺手加一列 ——
加一列会连带影响族谱、对照表的排行、以及"N 套都这样"这类结论的分量。

**② 的校正要写进材料,不要悄悄改掉** —— 论文与实现的差异标出了论文省略的工程约束,
比论文原文更有信息量。

**③ 的对照表按不变量排行**(领域概念、公式项、阶段),不按各家变量名排 ——
命名跨实现根本对不上,按名字排读者看不出差异。

**④ 一旦读者能自己推一遍,这条断言就不需要信任你。** 反推还顺带暴露量级错误:
算不出来的数,往往是某处单位或层级搞错了。

## 节的结构

一节按 **定位 → 领域模型 → 执行流图 → 代码对应 → 读法** 摆。两条容易漏的:

- **领域模型必须在代码之前**,且图与代码块**共用一套阶段编号** —— 否则读者要自己
  反推每段代码在算法里是哪一项
- **「读法」不能省** —— 图和代码只呈现事实,结论必须显式写出来

细节(代码块的三类旁注、读法的三种写法、横向对比节的额外部件)见
`references/document-skeleton.md`。

两条**改稿时才暴露**的纪律,单独指一下,因为它们都是增量写作的系统性偏差:

- **编号是命名空间**:主干只有一套段号;"关于主干的观察"另用 A/B/C;局部编号要当场声明。
  **而且两套编号不要长得一样** —— 实测中主干用 ①–⑫、另一处的"五个位置"也用 ①–⑤,
  一次全局替换就把后者串了,而"同小节内无冲突"的检查放行了它。
  改法:换记号(位置改用 P1–P5)。**批量重排编号前,先写出前后语义映射表,改完逐条核对。**
  见 `document-skeleton.md` 的"编号是命名空间",可测量的那一半用 `scripts/check_numbering.py`。
- **章节顺序是读者的依赖顺序,不是你的发现顺序**:全局视野与术语表几乎总是最后才写出来,
  于是最容易被留在后面。见 `material-anchoring.md` 的"章节顺序"。

## 先定位,再展开:开篇要给两张地图

一个具体题目在它所属的领域里几乎总是一个**子类**,而写的人浸久了会把子类当全类写。
读者拿到手,无法判断材料里的约束是这个领域的必然,还是你选的那条路线的代价。

**两张地图,缺任何一张读者都定位不了:**

| 轴 | 问题 | 缺了会怎样 |
|---|---|---|
| **任务轴** | 这个领域分几类任务,本文做哪一类 | 读者不知道材料对他适不适用 |
| **解法轴** | 这一类任务有哪几种解法,本文讲哪一种、为什么 | 读者会把某条路线的代价误当成领域的必然 |

解法轴最容易漏,因为作者一上来就选定了一条路线,后面全部深挖都在那条线上。
实测中这条是需求方拿着另一份材料回来提的。

**任务地图**:一张表,每行一个子类,列出**输入 → 输出**、**目标算在什么上**、
**代表实现**、**本文覆盖与否**。不覆盖的行也要点名代表实现 ——
写"其他方向"等于没写,读者无法判断自己关心的那个是不是被归进了"其他"。

**解法地图**:每条解法给足四样 —— **输入是什么(张量与形状)、输出是什么、
推理时一步做什么、训练时改成什么**。每条最好落到一个真实实现的行号;做不到就明写"未回源"。
代价不高:每条只需读到"训练目标那一行",不必展开它的工程细节。
再加一张**工程后果对照表**(各解法的串行步数、算力总量、显存形态),
读者才能判断为什么业界在某个场景下都选同一条。

**还有一件必须正面写的:目标是什么。**
损失/收益算在**哪些位置**上、哪些不算。这一条最容易因"不言自明"而整篇缺席 ——
它往往只以实现细节的形式散落着,从没被提炼成一句话。写它时带上:
一句话定义 + **它在代码里的落点(行号)**,以及**它支撑了后面哪几节**。
目标常常是全文结论的地基,换一个子类这条前提就不成立,那几节要重做。

**固定动作**:分类表里标出本文那一行,并写一句判别句 ——
"如果你要找的是 X,这份材料不适用;可迁移的只有第几节"。
子类限定要出现在**标题、主体章节开头、总纲、"未覆盖"**四处 ——
读者从任一入口进来都要能看到,只在开头写一次不够。

### 可读性是作者唯一无法自查的属性

事实可以核、结构可以数、图可以断言,唯独"这个词读者懂不懂"取决于读者已有的知识,
而作者在题目里泡过几天之后已经不在那个状态里。

**必须引入没泡在里面的视角,并且要给它具体人设**(会什么、不会什么、为什么读)。
只说"评估一下可读性"得到的是泛泛的好评;设定人设之后得到的是
"这一句里有三个我不认识的对象,这一节整段作废"这种可操作的判断。

**第二轮要换一个盲区不同的人设** —— 同一人设读第二遍只会确认第一遍。
两种视角抓的东西不重叠:

| 视角 | 抓到什么 |
|---|---|
| **扮演读者通读** | 语义与顺序:编号顺序与执行顺序相反、对象被归错类、引用指向别的函数、名词首次出现时无从理解 |
| **机械术语审计** | 一致性:术语先用后定义、同一个量两个记号、术语表条目正文其实没用过、裸缩写首现处无解释 |

**自检**:把材料交给一个只知道领域名的人,他能不能在读完第一屏后说出
"这份材料讲的是哪一种、目标是什么、不讲哪几种",以及
"本文这条路线与另外几条相比代价在哪"?两问有一问答不出,就是这一节缺了。

**需求方拿着别处的材料回来时**,通常不是那份更准,而是**它答了一个你没答的问题** ——
去识别那个问题,不要逐条比对细节。同时外部材料里的技术断言要当成**待核的假设**:
**它的作用是提问,不是提供事实。**

## 术语表:自造词是允许的,不定义不允许

"按领域模型组织、不按代码命名组织"(`references/material-anchoring.md`)必然导致
**你要用一批源码里不存在的词** —— 因为各家的标识符对不上,只能另起一个统称。
这是对的,但它有代价:读者拿这个词去 grep,一无所获。

实测反馈原话:"比如什么语言塔这些东西我就不知道是什么意思。"
写的人以为这是行话,读的人以为是源码里的东西,两边都不知道对方在想什么。

**规则:每个非日常词都要在术语表里出现,并标明它是哪一类。**

| 词源 | 含义 | 读者该怎么用它 |
|---|---|---|
| 源码词 | 源码里的标识符 | 可以直接 grep |
| 领域词 | 领域内通行,但各实现的标识符不同 | grep 不到,看对照列 |
| **本文用语** | 我为这份材料造的 | grep 不到,**且别处也没有** |

术语表要有一列"在各实现里叫什么",把领域词映射回每套实现的真实标识符 ——
这一列同时解决了两件事:读者能查,以及横向对照表的命名歧义。
放置位置与写法见 `references/document-skeleton.md`。

## 借口对照表

| 借口 | 实际情况 |
|---|---|
| "只改了一个词,不用重新生成" | 读者读的是产物。一个词也看不到。生成一次几秒钟 |
| "我在报告里说明了 HTML 会怎么渲染" | 推理过 ≠ 生成过。**实测最常见的失败正是这一条** |
| "生成脚本我没动,产物应该没问题" | 产物过期与脚本无关,与源文件改动有关 |
| "agent 已经把数值汇总好了" | 汇总表只是索引。层级归属最容易错,必须回源码 |
| "同事是这方面专家,他说的应该对" | 专家口述也要核。核出不成立,照实写并给证据 |
| "论文里就是这么画的" | 论文省略工程约束。画流水必须按真实容量算槽位 |
| "时间太紧,来不及核" | 错误进入成稿会扩散到正文/表格/图注/代码注释四处,改一处漏三处 |
| "这个数我记得是 X" | 记忆不是证据。grep 一次 |

## 危险信号 —— 出现就停下

按它们出现的阶段分组。同一条原则只列一次;具体是怎么栽的,看 `BASELINE.md`。

**取材与核实**

- 数值、层级、调用位置来自转述或名字推断,没 grep 过它的**使用点**
- 引用了行号,但没有回源机制;或只核到"存在",没核到"落在哪个定义、哪条执行路径"
- 联网取的仓库没记 commit + 日期,或没确认它**有你要写的那类路径**
- 从配置文件读了一组数就下结论,没算过它们的导出量(乘积、比值、极值)
- 写下"没有 X / 全都是 Y"这类全称判断,但没 grep 过反例
- 写下"N 套都这样",而样本里有同源的,且材料里没写明族谱
- 说"这里关了某个开关",但没确认它在当前条件下真的生效

**环境与工具**

- 写下"环境没有 X",但既没查过东西在不在,也没试过一种装法
- 生成产物时有告警,而流程退出码仍是 0

**结构与编号**

- 开篇没有定位:这个领域分几类、这一类有哪几种解法、本文的目标是什么
- 材料从它的第一节就开始讲分歧,没有一个从头走到尾的最小实例
- 编号没有被当成命名空间:同一符号指两件事、两套编号同形、顺序不是执行顺序、批量重排没有映射表
- 章节顺序是你的发现顺序,不是读者的依赖顺序
- 材料里出现源码里不存在的名字,而术语表里没有它

**demo**

- demo 没有闭合到题目里那个动词
- demo 散在各节而不是开篇一个;或被反馈两轮以上仍在打补丁
- 贴进正文的输出、代码、算法,没有机制证明它与实跑一致 —— 包括**读者按你给的规则算不出你给的数**
- 形状只报数字,不报每一维的含义与布局约定
- 图旁边没有产生这些数的公式与代码
- notebook 交付出去,但有格没有输出、或带着报错

**图**

- 图上的坐标是目测画的,不是按比例尺算的
- 图上有标注线,却说不出它标的位置是怎么算出来的
- 只跑了几何/计数检查就说图没问题 —— 断言的覆盖面要靠目检来长

**验收**

- 只靠自己判断"这个词读者懂不懂";或第二轮评审没换**盲区不同**的人设
- 拿到"调研一下 X"就直接开挖,没先摆出候选与差异轴让需求方收敛
- 准备说"完成"了,但没跑过生成命令

**这些都意味着:先去核,再落笔。**

## 三条纪律

**hedge 是纪律,不是含糊。** 核不到就不写、推断标成推断、runtime 值不编造总数、
省略显式标记。四种处理见 `references/evidence-grading.md`。

**治本不治标。** 同一类问题第二次出现时,改产生它的机制,不是躲开它的措辞。

**双向核验。** 质疑先默认成立去核;但权威口述核下来是错的同样常见,
不无条件采信任一方。

## 报告完成前的清单

同样按阶段分组。脚本名按你项目里的实际名字填 —— 这里只说该核什么。

**事实**

- [ ] 每个数值/常量都能指出来自哪个文件哪一行
- [ ] 行号引用有脚本回源,并排输出人工扫过一遍(含"落在哪个定义里")
- [ ] 每个函数的路径归属都 grep 过调用点
- [ ] 全称否定("没有 X""全都是 Y")都 grep 过反例
- [ ] 正文给出的每条算法/规则,自己按它手算过,能复现正文里的数
- [ ] 每个联网取的仓库都记了 commit + 日期,确认过它活着、且有你要的那类路径
- [ ] 横向对照的样本跨了族谱,同源关系已写明
- [ ] 范围经需求方确认过(或已写明"按默认范围 A 执行")

**结构**

- [ ] 开篇有领域分类表与解法清单,标出本文占哪一格、为什么选这条
- [ ] 求解的目标正面写出来了,并给了它在代码里的落点
- [ ] 子类限定出现在标题、主体开头、总纲、"未覆盖"四处
- [ ] 章节顺序是读者的依赖顺序
- [ ] 编号在全篇是一个命名空间:无冲突、两套不同形、顺序即执行顺序,重排后各部件同步
- [ ] 术语表覆盖全部非日常词,标了词源,领域词给了各实现的标识符
- [ ] 未覆盖的分支已写明(区分"我没讲"和"我不知道")

**demo**

- [ ] 有一个能跑的最小实例,闭合到题目里那个动词
- [ ] 每一格都有真实输出,贴进正文的数值经脚本比对过
- [ ] 每个张量都报了每一维的含义与布局约定
- [ ] 三个验收问题都能答"能",且单独发给没读过材料的人他能靠它入门

**产物**

- [ ] 跑过生成命令(不是推理过),产物与源文件同步
- [ ] 结构计数符合预期增量,渲染错误与占位符残留为 0
- [ ] 产物在浏览器里逐屏读回看过(装不上渲染器时,写明试过哪几种)
- [ ] 图有比例尺依据;流水图有 stall;每条并行边的依赖都论证过
- [ ] 找过没泡在题目里的视角读一遍(带人设),第二轮换了盲区不同的人设
- [ ] 试验性改动已回退,且回退后重新生成过
