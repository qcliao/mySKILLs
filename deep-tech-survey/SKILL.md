# 写可辩护的技术材料

**核心原则:材料里每一条断言都要能追到一个你亲自核过的事实,而读者看到的是产物、不是源文件。**

**动手顺序**:接到"调研一下 X"时,**先做范围勘察并把选择摆给需求方**(见"两个阶段"一节),
范围定了再进入下面的核实纪律。跳过这一步,做得再准也可能整节返工。

## 一、读者读的是产物,不是你改的那个文件

材料通常由 md 生成 HTML/PDF/PPT。这里有一个几乎无法自查的失败:**你改对了源文件,
产物却没重新生成** —— 于是读者还在看旧内容,而"我改好了"的感觉和"读者看到了"之间
没有任何东西会提醒你。实测中一个 agent 甚至在报告里推理了 HTML 的渲染结果,
却从头到尾没生成过它。

所以改完源文件、报告完成之前,跑一次生成 + 核对:

```bash
python build_html.py                 # 或该项目的生成命令

python <skill>/scripts/check_artifact.py 材料.md 材料.html \
    --expect "本次新增的串" --gone "本次删掉的串"
```

`check_artifact.py` 一次核三件事:产物 mtime 新于源文件、新串在两边都命中、
旧串在两边都消失。退出码非 0 就是不同步,别在这种状态下说完成。
(手工等价物:`grep -c` 两个文件 + `stat -c '%y %n'`。)

**项目里没有生成链路怎么办** —— 自己写一条,并把它当交付物的一部分(读者要能重跑)。
装不了依赖、没有浏览器时的取舍见 `references/output-forms.md` 开头那张判定表:
核心是**不要把断言托付给一条你无法验证的渲染路径**。

几个容易说服自己跳过的情形,其实都不成立:改动只有一个词、生成脚本没动过、
"我知道它会渲染成什么样"。前两个与产物是否过期无关,第三个是**推理**而非**生成**。

两点补充:

- **生成前确认目标文件没被程序占用**。被 PowerPoint / 编辑器锁住时,可能静默
  只写出一部分而不报错 —— 于是你拿到一个页数不全却看起来正常的产物。
- **回退改动时也要再生成一次**。试验、走错方向、需求变更导致源文件回退后,
  如果不重新生成,留下的是"产物比源文件新、内容却对不上"的更隐蔽的不一致。

**"已修改 X"只在有工具调用背书时才写得出来**,否则写"待生成"。

## 二、数值、层级、调用位置,只能来自你亲自读过的源码

论文、同事口述、subagent 汇总表 —— 这三者是**索引**,告诉你去哪个文件哪一行,
而不是可以直接落笔的事实。它们出错的方式很一致:细节对了,但**归属**错了。

所以最容易翻车的不是"这个数是多少",而是**"这个数是什么"**:

| 陷阱 | 具体表现 |
|---|---|
| 层级归属 | 把"切进下一级的粒度"当成"这一级本身",二者常差几倍 |
| 调用位置 | 把只在 backward 调的函数画进 forward 流程 |
| 切分用途 | 混淆"为并行而切""为装进下级存储而切""为搬运而切" |
| 签名漂移 | 返回值个数、常量按版本/硬件分叉 |
| 配置失效 | 精度开关因输入已是低精度而被静默忽略 |

**落笔前 grep 一次**:函数的所有调用点、常量的所有定义处。别看名字猜 ——
名字最像"就是那个东西"的时候恰恰最危险。

**还要问一句:它属于哪条执行路径?** 实测中两处翻车都是这样来的 ——
用 `class Inference` 里的一个常量论证**训练**侧的尺寸;
用只被采样循环调用的函数论证**训练**时的整除性质。
文件对、行号对、函数确实存在,**但那是另一条路径上的代码**。
所以行号校验实际有四层:**文件存在 → 行号不越界 → 落在哪个定义里 → 那个定义在哪条路径上**。
前三层机械可判(见第四节),第四层只能靠 grep 调用点。

**"没有 X"这类全称否定,写之前先 grep 一遍 X。**
实测中一轮就被推翻三条:"没有损失掩码"(另一条分支里有)、
"这是一条显存上限"(三个反例,而且全文没有任何显存测量)、
"其余三套都是同一种做法"(其中两套不是)。
成本是一次 grep,代价是整篇的可信度 —— 读者找到一个反例,就会开始怀疑别处。

一个具体的样子:

> 转述:"这个 kernel 的分块是 128。"
> 回源码:`128` 是切进下一级存储的粒度,这一级实际是 `512`,注释里写着 `512/128`。
> 落笔:`SingleN=512`,并注明 `128` 是切进 L1 的粒度 —— 两个数都留下,读者不会再误读。

写进材料的形态是"**值 + 它是什么 + 出处**",三者缺一就还没核完。

**从配置文件里取的数,还要自己算一遍导出量。** 配置里的数是**原料**,不是结论。
只读它们,读到的是设计者的意图轮廓,而意图与实际效果可以差很远。

实测:一份训练配置里 batch size 随帧数单调下降(45 → 12 → 6 → 4 → 3),
形状很像一条算力均衡曲线,我据此写下了"逐桶 batch size 用来拉平各桶计算量"。
把 33 个桶的 `序列长度 × batch size` 乘出来之后这句话不成立 ——
每步 token 数相差 **4.5 倍**,真实规律是"按区间内最长的桶定,顶到同一条显存上限"。

**固定动作:配置里的每组数,至少算一个导出量(乘积、比值、极值)再下判断**,
并把这个计算放进 demo —— 它同时成了可复核的实证。

**常量的名字是作者的说法,不是它的语义。** 同一轮里我把一个叫
`AE_SPATIAL_COMPRESSION` 的常量当成了自编码器的空间压缩率,据此推出"某些尺寸切不动"。
去读它**被用在哪里**才发现它是"压缩率 × patch"的合并步长,而且调用处用 `ceil`
保证了整除。**要判断一个常量是什么,看它的使用点,不看它的名字。**

## 三、代码是从网上取的时候,先确认它是不是现状

没有本地代码树时才联网取。这时**版本对不对**分两层,第二层是实测踩过的:

1. **锁 commit,不锁分支** —— 分支会漂移,读者按你写的行号就核不到。
2. **确认这个仓库还活着** —— 镜像能打开不等于镜像是现状。实测中一个仓的镜像可以正常
   访问、文件齐全,但 HEAD 停在九个月前,内容是一条"已迁移至别处"的通知;
   活跃仓库里同一个文件已经从 536 行长到 946 行。按镜像写完一整节后才发现,只能重来。

固定动作:取数前看一眼 **HEAD 的日期**与 **README 头部有没有迁移声明**;
两个来源都能访问时,逐文件比对行数,不同就以活跃的那个为准,并在材料里写明哪个是哪个。

3. **确认它有你要的那部分** —— 活跃、知名、星标高,都不代表它包含你要写的那条路径。
   实测中一个 17k 星的视频生成仓通过了前两条检查,但它顶层只有 `generate.py`,
   **全树 grep 不到任何 `train` / `finetune` 路径 —— 它是推理仓**。
   按"活跃且知名"选进样本,会读到写不出东西才发现。

   判据一句话:**把你要写的那一节的动词,拿去 grep 仓库的路径。**
   写训练就 grep `train`,写调度就 grep `schedul`,一条都没有就换候选。
   成本是一条命令。筛掉的候选要写进材料的"未覆盖",并说明筛掉的理由 ——
   读者会问"为什么没有它"。

**跨仓库的"同一个参数"要分别定位。** 同一个 API 在 A 仓已删除、在 B 仓仍在调用,
两件事可以同时成立 —— B 对齐的是 A 的旧版本。答案取决于问的是哪个仓的哪个 commit,
所以材料开头就要有一张"仓库 + commit + 日期"的表。

## 四、行号会漂,要有机制而不是靠细心

数值有 `grep` 兜底,**行号没有** —— 写错三行照样能编译、照样看起来像真的,
只有读者点开那一行才会发现对不上。实测中一次调研写了 130 多条 `文件:行号` 引用,
人工复核后仍有 4 条偏移 1–3 行,全部是脚本扫出来的。

做法是让脚本把"正文写的行号"与"该行的真实内容"并排打出来,人只负责扫一眼:

```bash
python <skill>/scripts/check_refs.py 材料.md --root <代码树根>
```

它能判定:文件存在、行号不越界、区间端点合法、短名引用是否有唯一候选。

**还差一层:行号落在哪个定义里。** 实测中两条引用通过了上面全部检查,却指向了别的函数
("损失的实现见 `x.py:263-270`",实际落在 `param_groups` 里)。
做法是从源码解析出顶层定义的行号区间,对每条引用报出**所属定义名**,
并对"从某个定义的中间切起"硬失败。细节见 `references/verification.md` 的三层表。
**自带 demo 的材料尤其要做这一层** —— demo 改得勤,正文里的引用不会跟着动。
它**判定不了**该行内容是否支撑正文 —— 这一项必须人看,但有了并排输出,
扫 130 条只要两分钟。重锚版本(见第三节)之后必须重跑一次:行号会整体平移。

## 五、覆盖面不够时,"一致"是假象

横向对照的两种结论里,**"一致处 = 硬约束"这一条只有在样本跨了实现族谱时才成立。**

实测教训:一次调研摆了三套实现,其中两套同源(一套基于另一套二次开发),
"三套都要求序列长度被并行因子整除"看起来像多模态的硬约束。补进第四套非同源实现
(不用多维并行的那一类)后,这条立刻降级成"多维并行的约束",与多模态本身无关。
**同源样本会把上游的实现选择伪装成领域的必然。**

三条固定动作:

- **按设计自由度的取值选样本,不按"我能拉到哪几个仓"选。** 每条差异轴至少要有
  两个不同取值,否则那条轴既不能证明是自由度,也不能证明是约束。
- **把族谱写进材料**:哪几套同源、谁是谁的下游、谁是独立实现。读者据此判断"一致"的分量。
- **覆盖不到的族要点名**:写"XX 这一类没覆盖,因为 YY",而不是"其他实现"。

## 六、最具象的解释是一个能跑的 demo

深度材料默认读者已经知道这件事整体怎么运转,而这个默认经常不成立 ——
实测反馈原话是"如果我都不知道这东西是怎么做的,我看这个就完全看不懂"。

补法不是加一段背景介绍(那只是换个地方罗列名词),而是**在分歧分析之前,
先把一个最小的完整实例从头走到尾**。而实例的最强形态不是文字描述,是**一段真能跑的代码**:
需求方的原话是"demo 是一种最具象的表现形式"。

### 验收标准是读者能上手,不是作者觉得讲清了

demo 的目的只有一个:**让一个不懂这行的人真正入门。**
"我把流程讲了一遍"不是达标,读者能不能接着往下走才是。三个验收问题,
逐条问自己,答不出就是没达标:

| 验收问题 | 不达标的样子 |
|---|---|
| 读者能说出**每个数是怎么来的**吗? | 只报 `1024`,没有 `(H/P)×(W/P)`,也没有算出它的那行代码 |
| 读者能**改一个参数并预测结果**吗? | 没有"变一变"那一格,读者不知道哪些量会跟着动 |
| 读者能**在真实仓库里找到对应位置**吗? | demo 与源码之间没有映射表,读完仍不知道该去看哪个文件 |

还有一条更硬的自查:**把 demo 单独拿出去发给一个没读过材料的人,他能不能靠它入门?**
不能,就说明它还依赖着正文里的上下文 —— 而正文的读者恰恰是靠 demo 才读得下去的。

### 投入要与它的权重相称:这是全篇性价比最高的一段

**后面所有章节都挂在 demo 上**:每一节都在讲"这一步各家怎么不同",
而"这一步是什么"只在 demo 里讲一次。它错一分,后面每一节都跟着错一分。

所以它值得按主干投入,而不是收尾时补一个附录。一个粗略的比例:
**demo 及其配套(代码、notebook、图、校验脚本)占整个交付的两到三成工时是正常的。**

### 反模式:轻描淡写

实测中这条被点名过:"你这个 demo 的目的是很重大的,你真的需要重视,为什么总是轻描淡写。"
"轻描淡写"有固定的几种样子,出现任何一种就是没达标:

- **只给结论不给中间量** —— 说"图被编码成 256 个 token",不给 1024 → 256 那一步的形状与代码
- **形状不带语义** —— `[1024, 588]` 而不是 `(N_patch=1024, 3*P*P=588)`
- **跑到一半就停** —— 停在"数据变成张量",而题目是训练(见下一节)
- **图没有代码、代码没有出处** —— 读者既不知道怎么算的,也不知道去哪核
- **一次只补一点** —— 这是最隐蔽的一种:每轮反馈只加一小块,看起来在推进,
  实际上每一轮都没达到验收标准。**判据不满足时应当重做那一节,而不是打补丁。**
  实测中这个 demo 被要求返工三轮才达标,三轮的共同原因就是每次只做了增量。

### 位置:开篇一个,全篇只有一个

**demo 是入口的桥,不是散在各节的插图。** 需求方把这条说得最清楚:
"最开始的 demo 对于用户来说已经有了一个全局的视野,也知道后面的细节具体的目标是什么。"

推论有两条,都要照做:

- **放在最前面,并且只放一个。** 后面各节不再重复"这一步是干什么的",
  只讲"各家在这一步的选择不同在哪"。每节都塞一个小 demo 会把主线切碎,
  而且读者第二次看到同一段骨架就会开始跳读。
- **它要能承重。** 既然后面所有细节都挂在它上面,它就必须**穷尽整条主干**:
  从输入一路到反向,一步都不能省。省掉的那一步,后面引用它时读者就断了。

判断这座桥搭得够不够,有一个直接的检验:**读完 demo,读者能不能说出后面每一节
要解决的是哪一环?** 说不出来,就是桥没搭到岸 —— 补法是在 demo 末尾加一张
"这一步 → 它在真实系统里立刻变成什么问题 → 去哪一节"的对照表。

### 这个 demo 是什么、不是什么

**不是**任何一套实现的简化版 —— 那样它就变成了第 N+1 套实现,还得解释它跟谁像。
**是**把 N 套实现**共有的那条骨架**单独拿出来:**少一步跑不通,多一步就不再是各家共有的。**
并行、打包、精度、拓扑这些差异全部拿掉 —— 它们是后面各节的主题,放进来第一步就接不上。

五条判据:

- **覆盖到领域的完整回路,而不是只到"数据变成张量"。** 这条最容易漏,后果最大 ——
  见下面单独一段。
- **具体到能对号入座**:用真实常量而不是 N 和 M(例:一张 448×448 的图 → 1024 个 patch
  → 256 个 token),读者能把自己的场景代进去。
- **每个张量都要报清每一维是什么**。只打印 `[1024, 588]` 等于没说 ——
  要写成 `(N_patch=1024, 3*P*P=588)`,并说明哪一维受什么约束、布局是 `[B,S,H]` 还是 `[S,B,H]`。
  跨实现的布局差异会让读者在真实代码里到处撞见转置,不先讲清就一直是谜。
- **只有一条路径**:不要出现分支。分支是后面各节的事,放进来就不"最小"了。
- **依赖尽量少**:能 CPU 跑完的规模。宽度可以缩,**但形状规律那一列必须与真实一致** ——
  并注明哪些数缩过、哪些没缩。

### 最容易漏的一条:回路要闭到题目上,而不是闭到"数据变成张量"

**判据是一句反问:题目里那个名词,在 demo 里有对应的代码吗?**

材料叫"训练框架",demo 就必须真的训练。只跑到"前向 + 一次反向"的 demo 看起来很完整 ——
前向有了、反向有了、梯度非零 —— 但参数怎么被更新、谁在训谁冻着、优化器状态占多少、
批次里形状不齐怎么办,一个都没出现。**这样的 demo 讲的其实是数据预处理**,
而读者会以为那就是这个领域的全部。

实测中这条是被直接指出来的:"你一直跟我说的都是数据预处理,具体训练你完全没提。"
当时我自认为满足了"闭合"这条判据 —— 但闭合的是前向反向那条链,不是训练这件事。

| 题目是 | demo 至少要跑到 | 只跑到这里就是跑偏 |
|---|---|---|
| 训练框架 | 参数分组与冻结、优化器状态、多步更新、批次组织 | 前向 + 反向 |
| 推理引擎 | 缓存的分配与复用、批次调度、采样 | 单条前向 |
| 数据管线 | 落盘格式、乱序与恢复、多进程切分 | 单条样本的变换 |
| 某个算子 | 与参考实现的数值比对、边界形状 | 跑通一次调用 |

以训练类为例,终点清单(其他领域按同样方式各自列一份):

| 缺了它就不算训练 | 它揭示什么 |
|---|---|
| 参数分组与冻结 | 三段结构的第一个实际后果:哪些参数真的在训 |
| 优化器状态的字节数 | 冻结省下的主要不是梯度,是优化器状态那两份 |
| 多步训练 + loss 曲线 | 接线到底通不通 |
| 一个"本步不参与"的样本 | 多卡下梯度分母对不上的由来 |
| 变长批次的浪费 | 打包这类机制的动机 |

**多步训练那一格要用"固定小批次能不能过拟合"**,不要用"每步换随机样本" ——
后者标签是噪声,loss 不降只能说明数据没得学,证明不了接线对不对。
(实测中第一版正是这么写的,跑出来 loss 从 6.93 涨到 7.75;改成固定小批次后 6.9956 → 0.0007。)
把这条写进 demo,读者顺带学到了怎么自查自己的训练脚本。

### 每一步都要三件套:公式 → 代码 → 图

只放图不行。实测反馈:"直接把每个图放上去了,把相关代码也放一下吧,
要不然不知道怎么算的,最好还有个公式。"三样东西各自回答一个不同的问题:

| 部件 | 回答 | 缺了会怎样 |
|---|---|---|
| **公式** | 这个数**是什么** | 读者只看到 1024,不知道它是 `(H/P)×(W/P)` |
| **代码** | 它**怎么算出来的** | 读者信不过那个数,也没法改参数试 |
| **图** | 它**长什么样** | 形状变化只能靠脑补 |

顺序固定:**公式在代码之前**(与标准节模板的"领域模型在代码之前"是同一条),
图在最后,再跟一句读法。另外把全篇的几条公式**先集中列一遍**再分步展开 ——
读者先看到骨架,再看每根骨头。

代码要贴**真实跑的那段**,带文件与行号,并让校验脚本核对它与源文件逐字一致 ——
贴进正文的代码和贴进正文的输出一样,会悄悄过期。

### 形态:notebook 优先,分阶段看中间结果

一次打完所有输出的脚本,读者只能从头读到尾;notebook 可以**一格一格看形状怎么变**,
配图就摆在那一格下面。实测反馈:"最好是一个 ipynb,这样可以分阶段看到一些结果,更加直观。"

四条约定:

- **逻辑只写一次。** 脚本版与 notebook 版是同一段逻辑的两种呈现 —— 逻辑放进一个模块,
  两边都 import 它。讲到某个函数时用 `inspect.getsource` 把**真正跑的那段源码**打出来,
  而不是在 notebook 里另抄一遍(抄的那份一定会漂)。
- **每一格配一张图。** 形状变化用图比用数字快一个量级:切格的网格、拼接前后的序列构成、
  损失掩码的分布、梯度到没到。
- **最后加一格"变一变"。** 把一个输入参数改掉,让读者亲眼看到哪些数跟着变 ——
  这一格往往比前面所有格加起来更能说明问题为什么难。
- **每一格的输出必须是真跑出来的。** 手写进 JSON 的"输出"等于把程序结果变成你写的字。
  没有 jupyter 也能做到:逐格 `exec`、捕获 stdout 与图,写进 nbformat 的 `outputs`。

### demo 与材料之间要有校验

把 demo 的输出贴进正文的那一刻,它就变成了"我写的字",与"程序打印的东西"之间
再没有任何东西保证一致 —— 改了 demo 忘了改正文不会有任何症状。
这与"改了源文件忘了重新生成产物"是同一类失败,所以用同一种办法:**重跑 + 比对**。

```bash
python <skill>/scripts/check_notebook.py demo/x.ipynb   # notebook 是否完整执行、有无报错格
```

正文里贴的形状与数值,要有一个项目内的脚本重跑 demo 再逐个比对(做法见
`references/verification.md`)。**demo 是交付物的一部分,不是附件。**

## 两个阶段:先勘察并反问,再深入核实

**"调研一下 X"是一句范围未定的需求。** 直接挑几套实现深入,等于替需求方做了他没做的决定 ——
而这个决定通常是错的:实测中一份调研深挖了三套实现、每条断言都可核,交付后第一反应是
"torch 原生那一套呢?"。**深度做满了,范围没对上,返工的是整节。**

所以分两个阶段,中间有一个**必须停下来问人的点**。

### 阶段一:范围勘察(浅、快、不下结论)

目标不是回答问题,是**把选择摆到需求方面前**。产出四样东西,加起来控制在一屏内:

| 产出 | 内容 | 判据 |
|---|---|---|
| 候选清单 | 有哪些实现/方案,**按族谱分组并标血缘** | 同源的要合并成一组,别当成多个候选 |
| 差异轴清单 | 打算比什么(不是"比一比",是具体的轴) | 每条轴要能说出"取值可能有哪几种" |
| 取数成本 | 每个候选:代码能不能拿到、有没有官方文档 | 拿不到的要现在说,不要写到一半才发现 |
| **待确认问题** | 3–5 个,**每个都要影响后续做什么** | 答案不改变工作内容的问题,不要问 |

勘察阶段**不读实现细节、不记行号**。这一阶段的错误成本是几分钟,深入之后是整节。

### 收敛点:哪些必须问,哪些自己定

问不问的判据只有一条:**不同答案会不会导致做的事不一样。**

| 必须问 | 自己定 |
|---|---|
| 覆盖哪些族(以及明确排除哪些) | 每套实现从哪个文件读起 |
| 深度优先(2 套挖透)还是广度优先(6 套各摸一层) | 用什么图、几张图 |
| 读者是谁(决定要不要术语表、最小实例的起点) | 章节怎么分 |
| 有没有必须落地的目标栈(决定哪套是主角) | 用哪些校验脚本 |

把问题连同**你的默认选项**一起给出("不指定的话我按 A 做"),需求方点头即可,不必逐条回答。

### 阶段二:深入核实(四步主循环)

范围确认之后才开始,这时才谈行号。

| 步 | 做什么 | 产出 |
|---|---|---|
| ① 论文 | 拿骨架 + 可引用坐标(章节号/图号) | 阶段表、权威出处链接 |
| ② 源码 | 逐条核对 ① 的先验 | **校正清单** —— 差异本身就是产出 |
| ③ 横向对照 | N 套实现摆一起,**且 N 要跨族谱**(第五节) | 分歧处 = 设计自由度,一致处 = 硬约束 |
| ④ 反推 | 用容量/带宽约束反解常量 | 把陈述变推导 |

**范围在阶段二中途变了,要回到收敛点重新确认**,而不是顺手加一列 ——
加一列会连带影响族谱、对照表的排行、以及"N 套都这样"这类结论的分量。

**② 的校正要写进材料,不要悄悄改掉** —— 论文与实现的差异标出了论文省略的工程约束,
比论文原文更有信息量。

**③ 的对照表按不变量排行**(领域概念、公式项、阶段),不按各家变量名排 ——
命名跨实现根本对不上,按名字排读者看不出差异。

**④ 一旦读者能自己推一遍,这条断言就不需要信任你。** 反推还顺带暴露量级错误:
算不出来的数,往往是某处单位或层级搞错了。

## 节的结构

一节按 **定位 → 领域模型 → 执行流图 → 代码对应 → 读法** 摆。两条容易漏的:

- **领域模型必须在代码之前**,且图与代码块**共用一套阶段编号** —— 否则读者要自己
  反推每段代码在算法里是哪一项
- **「读法」不能省** —— 图和代码只呈现事实,结论必须显式写出来

细节(代码块的三类旁注、读法的三种写法、横向对比节的额外部件)见
`references/document-skeleton.md`。

两条**改稿时才暴露**的纪律,单独指一下,因为它们都是增量写作的系统性偏差:

- **编号是命名空间**:主干只有一套段号;"关于主干的观察"另用 A/B/C;局部编号要当场声明。
  **而且两套编号不要长得一样** —— 实测中主干用 ①–⑫、另一处的"五个位置"也用 ①–⑤,
  一次全局替换就把后者串了,而"同小节内无冲突"的检查放行了它。
  改法:换记号(位置改用 P1–P5)。**批量重排编号前,先写出前后语义映射表,改完逐条核对。**
  见 `document-skeleton.md` 的"编号是命名空间",可测量的那一半用 `scripts/check_numbering.py`。
- **章节顺序是读者的依赖顺序,不是你的发现顺序**:全局视野与术语表几乎总是最后才写出来,
  于是最容易被留在后面。见 `material-anchoring.md` 的"章节顺序"。

## 先定位,再展开:题目几乎总是某个领域的一个子类

一个具体题目在它所属的领域里,几乎总是一个**子类**;而写的人浸在里面久了,
会不自觉地把子类当成全类来写 —— 全篇不出现"这个领域一共分几种",
因为对作者来说"讲的是哪一种"从第一天起就是默认的。

实测反馈原话(材料交付、全部校验通过之后的第一个问题):
**"这里面的 target 是什么?是 text?多模态应该有很多种类,文生图、文生视频、
视频生成,这几个类型在你的报告完全没有提到,我也不知道你这个讲的是哪一种。"**

那份材料其实写了范围,写在"本文的边界"一节的一个条目里:"明确不覆盖:纯生成方向……"。
**信息在,坐标系不在。** 差别是这样的:

| 写法 | 读者能不能定位自己 |
|---|---|
| "本文不覆盖 X、Y" | 不能 —— 他不知道一共有几类,也就不知道剩下的是哪一类 |
| 一张分类表 + 指出本文站在哪一行 | 能 |

**开篇要给两张地图,不是一张。** 它们是两条不同的轴,缺任何一条读者都定位不了:

| 轴 | 问题 | 缺了会怎样 |
|---|---|---|
| **任务轴** | 这个领域分几类任务,本文做哪一类 | 读者不知道材料对他适不适用 |
| **解法轴** | 这一类任务有哪几种解法,本文讲哪一种、为什么是它 | 读者会把某条路线的代价误当成领域的必然 |

解法轴最容易漏,因为作者往往一上来就选定了一条路线,后面全部的深挖都在那条线上,
于是**整篇没有一个地方交代"还有别的走法"**。实测中这条是需求方拿着另一份材料回来提的:
"我做这个 survey 首先需要知道一个全貌,到底有什么样的推理范式,以及对应的训练方法。"
当时那份材料从"一次训练迭代长什么样"讲起 —— 而那已经是**选定范式之后**的事。

**解法地图要给足四样**,少一样读者就对不上号:
**输入是什么(张量与形状)、输出是什么、推理时一步做什么、训练时改成什么。**
每一条最好落到一个真实实现的行号;做不到就明写"未回源"。
代价不高:每条解法只需要读到"训练目标那一行",不必展开它的工程细节。

再加一张**工程后果对照表**(各解法的串行步数、算力总量、显存形态),
读者才能判断为什么业界在某个场景下都选了同一条。

**两件必须在开篇正面写出来的事:**

**① 领域的分类,以及本文占哪一格。** 一张表,每行一个子类,列至少包括:
这一类的**输入 → 输出**、**代表实现**、**本文覆盖与否**。
不覆盖的行也要列出来并点名代表实现 —— 写"其他方向"等于没写,
读者无法判断自己关心的那个方向是不是被归进了"其他"。

**② 优化的目标是什么(target)。** 这是最容易被当成"不言自明"因而整篇缺席的一条:
损失/收益算在**哪些位置**上,哪些位置不算。它通常散落在代码细节里
(比如"标签在某些位置填 -100"),从没被提炼成一句话。

**为什么②比①更要紧:目标往往是全文结论的地基。** 上面那份材料的四个核心结论里,
至少两个直接建立在"视觉位置不产生 loss token"这条前提上 ——
换一个子类(生成方向),这条前提不成立,那两节要重做。
**地基没写出来,读者就无法判断这份材料对他适不适用**,
而这恰恰是他打开材料后要做的第一个判断。

**固定动作:**

- 开篇的分类表里,把本文那一行标出来,并写一句**判别句** ——
  "如果你要找的是 X,这份材料不适用;其中可迁移的只有第几节"。
- 正面写出目标,并给出它在 demo 或源码里的落点(行号)。
- 写清这条前提**支撑了哪几节**,以及换子类之后哪几节要重做;
  在"未覆盖"一节回指分类表,不要另起一套说法。
- 标题、主体章节的开头、总纲、"未覆盖"这几处**同时**加上子类限定 ——
  读者从任一入口进来都要能看到,只在开头写一次不够。

**可读性是作者唯一无法自查的属性。** 事实可以核、结构可以数、图可以断言,
唯独"这个词读者懂不懂"取决于读者已有的知识,而作者在题目里泡过几天之后
已经不在那个状态里。**必须引入一个没泡在里面的视角**,并且要给它**具体人设**;
**第二轮要换一个盲区不同的人设** —— 同一人设读第二遍只会确认第一遍。
实测中第一个人设是"会 LLM 训练、不懂扩散",第二个换成"懂扩散、不懂分布式",
两轮抓到的问题几乎不重叠,而且第二轮直接推翻了若干断言。人设的价值在于**它的盲区**:
读者卡住的地方,正是材料默认了他不具备的那部分知识。

人设举例 ——
"会 Transformer 与并行、不懂扩散,读这份材料是为了搞懂 X"。
只说"评估一下可读性"得到的是泛泛的好评;设定人设之后得到的是
"这一句里有三个我不认识的对象,这一节整段作废"这种可操作的判断。

两种视角要一起上,它们抓的东西不重叠:

| 视角 | 抓到什么 |
|---|---|
| **扮演读者通读** | 语义与顺序:编号顺序与执行顺序相反、对象被归错类、行号指向别的函数、名词首次出现时无从理解 |
| **机械术语审计** | 一致性:术语先用后定义、同一个量两个记号、术语表条目正文其实没用过、裸缩写首现处无解释 |

**自检**(在"报告完成前的清单"里也列了):
把材料交给一个只知道领域名、不知道你选题的人,他能不能在**读完第一屏**之后说出
"这份材料讲的是这个领域里的哪一种,目标是什么,不讲哪几种"?
再加一问:他能不能说出"本文选的这条路线,与另外几条相比代价在哪、优势在哪"?
两问有一问答不出,就是这一节缺了。

**关于"需求方拿着别处的材料回来"这件事**:通常不是那份材料更准,
而是**它答了一个你没答的问题**。正确的反应是去识别那个问题,而不是逐条比对细节。
实测中那份外部材料的具体数字一条都没能回源核实,但它提的问题是对的 ——
**问题的价值与答案的可靠性是两件独立的事。**
顺带一提:外部材料里的技术断言要当成**待核的假设**。同一份材料里有一条
"某个调制参数只依赖时间步,因此可预计算并卸载权重",去读实现发现它还依赖文本向量,
换一句提示词就要重算 —— **外部材料的作用是提问,不是提供事实。**

## 术语表:自造词是允许的,不定义不允许

"按领域模型组织、不按代码命名组织"(`references/material-anchoring.md`)必然导致
**你要用一批源码里不存在的词** —— 因为各家的标识符对不上,只能另起一个统称。
这是对的,但它有代价:读者拿这个词去 grep,一无所获。

实测反馈原话:"比如什么语言塔这些东西我就不知道是什么意思。"
写的人以为这是行话,读的人以为是源码里的东西,两边都不知道对方在想什么。

**规则:每个非日常词都要在术语表里出现,并标明它是哪一类。**

| 词源 | 含义 | 读者该怎么用它 |
|---|---|---|
| 源码词 | 源码里的标识符 | 可以直接 grep |
| 领域词 | 领域内通行,但各实现的标识符不同 | grep 不到,看对照列 |
| **本文用语** | 我为这份材料造的 | grep 不到,**且别处也没有** |

术语表要有一列"在各实现里叫什么",把领域词映射回每套实现的真实标识符 ——
这一列同时解决了两件事:读者能查,以及横向对照表的命名歧义。
放置位置与写法见 `references/document-skeleton.md`。

## 借口对照表

| 借口 | 实际情况 |
|---|---|
| "只改了一个词,不用重新生成" | 读者读的是产物。一个词也看不到。生成一次几秒钟 |
| "我在报告里说明了 HTML 会怎么渲染" | 推理过 ≠ 生成过。**实测最常见的失败正是这一条** |
| "生成脚本我没动,产物应该没问题" | 产物过期与脚本无关,与源文件改动有关 |
| "agent 已经把数值汇总好了" | 汇总表只是索引。层级归属最容易错,必须回源码 |
| "同事是这方面专家,他说的应该对" | 专家口述也要核。核出不成立,照实写并给证据 |
| "论文里就是这么画的" | 论文省略工程约束。画流水必须按真实容量算槽位 |
| "时间太紧,来不及核" | 错误进入成稿会扩散到正文/表格/图注/代码注释四处,改一处漏三处 |
| "这个数我记得是 X" | 记忆不是证据。grep 一次 |

## 危险信号 —— 出现就停下

- 准备说"完成"了,但没跑过生成命令
- 手上的数字来自 subagent 的汇总表,没回源码核
- 流水图里没有任何 stall / 阻塞条
- 图上的尺寸是目测画的,不是脚本按比例尺算的
- 写下了一个函数在某条路径上,但没 grep 过它的调用点
- 材料里出现了源码里不存在的名字,而术语表里没有它(自造词本身没问题,不定义才是问题)
- 说"这里关了某个精度模式",但没确认它在当前 dtype 下真的生效
- 联网取的代码,没看过该仓库 HEAD 的日期
- 写下"环境没有浏览器/没有某工具",但一种安装办法都没试过
- 把**工具的报错**当成**环境的结论**(工具说找不到 ≠ 东西不在盘上 —— 先 find / fc-list / which 看一眼)
- 图上有标注线,却说不出它标的位置是怎么算出来的
- 只跑了几何/计数检查就说图没问题 —— 断言的覆盖面要靠目检来长
- 写下"N 套实现都这样",但这 N 套里有同源的,且没在材料里说明
- 材料从第一节就开始讲分歧,没有一个从头走到尾的最小实例
- demo 的输出或代码贴进了正文,但没有任何脚本能证明它与实跑/源文件一致
- 正文里摆了一串图,却没有产生这些数的公式与代码
- demo 走到前向反向就停了,而材料讲的是训练/推理/部署 —— 那 demo 只讲了数据预处理
- 打印了形状却没说每一维是什么,也没交代布局约定
- demo 散在各节,而不是开篇一个能承重的
- 同一个编号(①②③…)在材料里指两件不同的事,或"关于主干的观察"占了段号
- 全局视野排在细节之后 —— 通常是因为它最后才写出来,被顺手追加在了末尾
- 材料题目里的核心名词(训练/推理/调度…),在 demo 里找不到对应的代码
- demo 被反馈了两轮以上还没达标 —— 说明在打补丁,该重做了
- 打印了形状却没说每一维是什么 —— `[1024, 588]` 等于没说
- notebook 交付出去,但其中有格没有输出、或带着报错
- 引用了几十条行号,但没有任何机制回源核过
- 行号核过了"存在且不越界",但没核过"它落在哪个函数里"
- 材料里的编号(①②③…)按讲述方便排,而不是按真实执行顺序排
- 只靠自己判断"这个词读者懂不懂" —— 泡在题目里的人做不了这个判断
- 写下"没有 X / 全都是 Y"这类全称判断,但没 grep 过反例
- 引用的那行确实存在,但没确认它属于**哪条执行路径**(训练 / 推理 / 校验)
- 批量重排过编号,但没有前后语义映射表,也没检查另一套编号有没有被同一个替换命中
- 第二轮评审换的是人,没换**人设** —— 同一盲区读两遍只会确认第一遍
- 拿到"调研一下 X"就直接开挖,没有先摆出候选与差异轴让需求方收敛范围
- 中途加了一套实现,但没回头修族谱与"N 套都这样"这类结论
- 把一个仓选进样本,但没 grep 过它有没有你要写的那类路径(推理仓与训练仓长得很像)
- 从配置文件里读了一组数就下结论,没有算过它们的乘积/比值/极值
- 根据常量的**名字**推断它的语义,没有去看它的使用点
- 全篇没有一张"这个领域分几类、本文占哪一格"的表 —— 只写了"不覆盖 X",没给坐标系
- 全篇没有交代"这一类问题还有哪几种解法" —— 深挖的是一条路线,写得却像整个领域
- 说不出这份材料优化/求解的**目标**是什么(损失算在哪些位置、哪些不算),或者它只以代码细节的形式散落在正文里

**这些都意味着:先去核,再落笔。**

## 三条纪律

**hedge 是纪律,不是含糊。** 核不到就不写、推断标成推断、runtime 值不编造总数、
省略显式标记。四种处理见 `references/evidence-grading.md`。

**治本不治标。** 同一类问题第二次出现时,改产生它的机制,不是躲开它的措辞。

**双向核验。** 质疑先默认成立去核;但权威口述核下来是错的同样常见,
不无条件采信任一方。
